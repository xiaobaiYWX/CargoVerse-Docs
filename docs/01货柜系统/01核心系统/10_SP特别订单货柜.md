# SP 特别订单货柜

> 设计稿／尚未实现。本文确定 SP 的系统身份、数据边界与运输闭环；具体订单内容、出现条件、奖励曲线和终端交互仍需后续设计与实现。

## 核心定义

SP 是 `Special Order`，表示一份随货柜实体一同生成的特殊运输订单，不是 S/M/L/X/XL 之后的更高货柜等级。

普通货柜是玩家长期持有、可以反复装卸不同 CargoGood 的运输设备；SP 货柜则是订单方临时交给玩家运输的封存资产。SP 货柜生成时同时生成并冻结货柜、货物与订单数据，只能按订单整柜交付，不能作为普通空柜循环使用。

| 项目 | 普通货柜 | SP 特别订单货柜 |
| --- | --- | --- |
| 系统身份 | 玩家拥有的运输设备 | 订单方委托保管的封存运输资产 |
| 规格 | S/M/L/X/XL，具有常规递进关系 | SP，仅表示特别订单类别，不参与大小排序 |
| 取得方式 | 在货柜制造台制造空柜 | 接受特殊订单时由订单系统直接生成载货柜 |
| 许可证 | 按制造配方要求检查许可证等级 | 不设 SP 许可证等级，不与常规等级比较 |
| 初始内容 | 空 Load | 生成时即写入完整 Load 与订单快照 |
| 装卸 | 可装载、部分卸载、卸空、重新装载 | 禁止装载、补装、部分卸载、换货和清空 |
| 结算 | 按实际卸货数量和当前市场价格结算 | 只在指定目的地按整份订单结算 |
| 交付后 | 保留空柜，继续归玩家所有 | 整柜移交并从世界与活动资产中移除 |

`SP` 可以继续作为容器 `size_class` 的特殊枚举值，用于数据校验、显示和资源分类，但任何等级排序、许可证门槛、雷达规格倍率与常规调度点预算都不得把它当成第六档。

## 货柜、货物与订单分层

SP 不应把所有业务字段塞进现有货柜容器定义。建议保留三层数据：

```text
SP 容器定义
└─ 描述可生成的物理外壳：结构、厂商、质量、耐久、容量、设计特性

特别订单定义
└─ 描述如何生成一类订单：候选外壳、候选货物、数量、起讫条件、奖励与失败规则

特别订单实例
└─ 某次生成后冻结的实际结果，并绑定唯一 SP 货柜资产
```

容器定义仍位于 `cargo_containers`，`size_class` 为 `SP`。它只负责物理设备能力，不代表该型号能够从货柜制造台制造，也不提供普通装载兼容性入口。

特别订单定义建议使用独立目录：

```text
data/<namespace>/special_orders/<path>.json
```

订单定义可以引用一个确定的 SP 容器，也可以提供加权容器池；可以引用确定的 CargoGood，也可以提供候选池和数量范围。所有抽取只在实际生成货柜时进行一次。

## 生成时冻结的快照

接受订单并生成实体时，服务端在同一事务中完成以下工作：

1. 再次确认订单仍可领取、玩家没有重复领取且生成区域可用；
2. 抽取并解析 SP 容器、CargoGood、数量、运输要求、目的地、时限和奖励；
3. 创建唯一 `specialOrderInstanceId` 与封条编号；
4. 写入容器快照、货物快照和订单快照；
5. 以已经装货的目标总质量生成物理结构和货物贴花；
6. 全部成功后才把订单标记为运输中。

任一步失败都回滚本次生成，不留下空壳、无主资产或已经占用的订单。

冻结的是订单事实，而不是运输过程中必然变化的状态：

| 生成后不可修改 | 运输中允许变化 |
| --- | --- |
| 订单定义 ID、容器定义 ID与设备快照 | 物理位置、物理结构映射 |
| CargoGood 快照、货物数量 | 货物完整度、词条计时与词条运行状态 |
| 起点、唯一目的地、委托方 | 货柜耐久与损伤状态 |
| 基础奖励、奖励币种、时限、完整度门槛 | 订单状态与状态变更时间 |
| 封条编号与订单规则 | 可由规则推导的最终奖励预览 |

这里的“不可修改”必须由服务端交易入口强制执行，不能只依赖客户端隐藏按钮。数据包重载也不得重算已经生成的 SP 实例。

第一版沿用现有 `CargoLoad`，因此一个 SP 货柜只保存一种具体 CargoGood 和一个固定整数数量。需要表现复合设备、聚落模块或未知遗物时，应把整套内容定义为一个 CargoGood；多货种清单等以后确有玩法需求时再扩展，不在第一版提前引入。

## 与常规系统隔离

### 许可证和取得条件

SP 不进入常规运输许可证的 S/M/L/X/XL 等级表，也不增加“SP 许可证”。普通制造校验遇到 `size_class = SP` 时应始终拒绝。

特别订单是否可见、可领取，应由订单自己的条件决定，例如：

- 指定贸易点或贸易点类型；
- 贸易点繁荣度；
- 制造商／委托方声望；
- 前置任务、世界事件或一次性标记；
- 玩家当前进行中的特别订单数量。

可以要求玩家已经登记运输档案，以便记录承运人身份，但不得再比较常规许可证等级。

### 所有权和调度点

SP 是受托资产，不应计入“玩家永久拥有的货柜”，也不应消耗按许可证提供的常规货柜调度点。玩家在运输期间仍作为唯一承运人，用于交互权限、保护与交付校验。

为了防止无限领取，应使用独立的“进行中特别订单数量”限制。默认建议每名玩家同时进行 1 份；具体订单可以显式覆盖。这个限制属于订单系统，不随许可证升级增长。

### 装卸、维修和普通收购

处于运输中的 SP 货柜必须被以下入口拒绝：

- 货柜装载机与管理员补装命令；
- 货物卸载机，包括部分卸货和整批卸空；
- 货柜机械台的清理、改装或改变清单的操作；
- 旧整柜收购入口与任何按市场价出售整柜的入口；
- 普通销毁／回收入口。

维修是否允许应按维修行为区分：恢复货柜耐久但不打开封条的外部维修可以作为以后玩法；任何会改变 Load、订单快照或封条状态的操作都必须禁止。

## 交付与结算

SP 使用专用交付校验，不按目的地当前是否收购该 CargoGood 判断，也不采用普通市场浮动价格。

一次有效交付必须同时满足：

1. 操作者是订单承运人；
2. 货柜仍绑定原订单实例，封条有效；
3. 当前贸易点与快照中的唯一目的地匹配；
4. CargoGood、数量和不可变订单字段与生成快照一致；
5. 订单未完成、未失败，也没有正在执行的重复结算；
6. 达到订单配置的时限、完整度或货柜耐久要求。

交付事务建议按以下顺序执行：锁定订单与货柜、重新校验、计算奖励、发放奖励、写入完成记录、移除物理货柜、移除活动资产、释放特别订单名额。任一步失败都必须补偿，防止重复领奖或交付后残留货柜。

交付后的货柜不变为空柜，也不转为普通玩家资产；它与货物一起被订单方接收并从世界移除。玩家档案只保留轻量的历史摘要，用于统计、成就和后续声望计算。

奖励是订单生成时冻结的合同奖励，不是货物售价。推荐公式为：

```text
最终奖励 = 基础奖励 × 时效系数 × 货物完整度系数 × 货柜状态系数
```

各系数的规则和上下限也必须在生成时快照。若订单要求不满足，可按订单配置选择拒收、降额接收或判定失败；第一版建议仅支持“满足门槛后按系数结算”和“不满足门槛则拒收”两种明确结果。

SP 交付不增加常规许可证经验，也不直接走普通贸易点 CargoGood 买卖记账。后续若加入委托方声望，应作为独立奖励字段。

## 订单状态

建议使用最小状态机：

```text
可领取 → 生成中 → 运输中 → 交付中 → 已完成
                 └──────────→ 已失败
```

- `可领取` 是订单候选，不对应货柜资产；
- `生成中` 只存在于事务内，服务器重启后不应留下该稳定状态；
- `运输中` 是唯一可操作的活动状态；
- `交付中` 用于阻止重复点击和并发结算；
- `已完成` 与 `已失败` 只保留历史摘要，不再绑定活动物理货柜。

货柜实体意外丢失、被破坏或长时间无法恢复时，不应静默生成替代品。订单进入可诊断的异常／失败处理流程，是否允许重新生成由具体订单规则决定。

## 建议的订单定义示例

以下仅用于确定职责边界，不是已实现的数据契约：

```json
{
  "schema_version": 1,
  "display_name": "前文明样本紧急转运",
  "issuer": "cargoverse:hri",
  "containers": [
    { "id": "cargoverse:hri/genesis_si_sp", "weight": 1 }
  ],
  "cargo": {
    "goods": [
      { "id": "cargoverse:research_sample/ancient_sample", "weight": 1 }
    ],
    "units": { "min": 1, "max": 1 }
  },
  "destination": {
    "trade_point_tags": ["hri_research_port"]
  },
  "reward": {
    "currency": "cargoverse:enderite",
    "amount": { "min": 1200, "max": 1600 }
  },
  "rules": {
    "time_limit_ticks": 72000,
    "minimum_integrity_ratio": 0.8,
    "minimum_durability_ratio": 0.5,
    "max_active_per_player": 1
  }
}
```

即使定义中使用范围和候选池，生成后的实例也必须只保存确定结果，不保存“下次读取时再抽”的随机表达式。

## 实现落点

现有代码已经具备可复用基础：`CargoContainerInstance`、`CargoContainerSnapshot`、`CargoLoad`、物理生成／移除、货物词条、完整度与事务补偿。实现 SP 时仍需要新增明确身份与订单绑定，不能仅凭 `sizeClass == SP` 分散判断。

建议新增：

- 货柜资产来源／用途字段，例如普通自有资产与 SP 受托资产；
- `SpecialOrderDefinition` 与重载监听；
- `SpecialOrderInstance` 与独立 SavedData；
- 生成即装货的 SP 生成事务；
- 所有常规变更入口共用的“是否允许修改 Load”守卫；
- 专用整柜交付事务与历史摘要；
- SP 候选、运输中状态和目的地提示界面。

旧整柜收购代码可以复用物理移除等底层能力，但不能直接充当 SP 交付：它按市场收购、检查普通贸易点库存并发放许可证经验，与本文规则不一致。

## 第一版验收闭环

- [ ] SP 不出现在货柜制造台候选中，任何许可证等级都不能制造。
- [ ] 接单时一次性生成载货实体、不可变快照、订单绑定和正确总质量。
- [ ] SP 不占普通调度点，只占独立的进行中订单名额。
- [ ] 装载、部分卸载、换货、普通整柜出售和管理员补装均被服务端拒绝。
- [ ] 数据包重载、服务器重启后，货物、数量、目的地、规则和奖励保持生成时结果。
- [ ] 错误贸易点不能交付；正确贸易点只能成功结算一次。
- [ ] 成功交付后整柜移除、活动实例结束、名额释放并留下历史摘要。
- [ ] 并发点击、奖励发放失败或物理移除暂时失败时不会复制奖励或留下可重复交付状态。
