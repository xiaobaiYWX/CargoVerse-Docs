## 1. 两层职责

- CargoClass：硬编码一级大类，只决定分类及公共贴花。数据包不能注册新的一级类。
- CargoGood：数据包中的具体货物，保存科技等级、标签、质量、价值、币种、经验、完整度、运输词条。
- 同一大类可以有多个具体货物。矿石、原木、石料都属于 raw_resource，但仍有各自独立的库存、价格、兼容性与装载状态。
- 当前是单一货物装载模型：同一个货柜不能因为两个货物属于同一 CargoClass 就混装；只有完整 CargoGood ID 相同才能尝试续装。

## 2. 数据文件与引用

```text
data/<namespace>/cargo_goods/<cargo_class>/<good>.json
             ↓
<namespace>:<cargo_class>/<good>
```

例如：

```text
data/cargoverse/cargo_goods/raw_resource/ore.json
→ cargoverse:raw_resource/ore

data/my_pack/cargo_goods/agriculture/rice.json
→ my_pack:agriculture/rice
```

ID 与 CargoClass 从路径获得，不在 JSON 重复填写 id、cargo_type 或 cargo_class。

```json
{
  "schema_version": 1,
  "display_name": "稻米",
  "tech_level": 2,
  "tags": [],
  "trade_currency": "cargoverse:enderite",
  "unit_mass": 2.0,
  "base_value": 10,
  "license_experience_per_unit": 1.0,
  "prosperity_experience_per_unit": 0.5,
  "base_integrity": 100.0,
  "transport_requirements": []
}
```

display_name 为直接字符串，不再解析货物翻译键。trade_currency 仍必须引用成功加载的 currency_groups，不接受普通物品 ID。

tech_level 是必填非负整数；tags 是普通字符串标签数组（省略时为空），禁止空白、重复或非字符串元素。二者暂仅供后续生产线查询，不影响当前交易结算。详细约束见 [货物定义](02_货物定义.md)。实际数据包不写注释。

添加一个可交易货物需要同时配置：

1. 其 CargoGood JSON。
2. 对应货柜的 allowed_cargo，例如 `["my_pack:agriculture/rice"]`。
3. 如需制造商针对该货物修正，在 cargo_modifiers 中使用同一完整 ID。
4. 在贸易点 sales.resources / acquisitions.resources 中按完整 ID 定义产出或需求；生产 inputs 也使用完整 ID。
5. 商店物品需要联动该货物库存时，填写 cargo_good；不关联货物的普通商品可以省略。

例如贸易点：

```json
{
  "display_name": "稻米港",
  "sales": {
    "resources": {
      "my_pack:agriculture/rice": {
        "stock_max": 500,
        "natural_cargo_units_increase": 10
      }
    }
  },
  "acquisitions": {"resources": {}}
}
```

## 4. 校验、回退与重载

- 合法货物 ID 必须具有命名空间与严格两段 class/good 路径，最长 256 字符。货物名称最长 256 字符，货物目录上限 16384 项。
- 不合法的贸易点货物键直接拒绝，不会归并为 none 库存。
- 数据包定义中一级类未知（例如 my_pack:future/rice）时正常加载并按 `none` 分类解析，使用 none 图标；不能通过目录名注册新 CargoClass。货物完整 ID 及具体数据保留，不会与 `my_pack:none/rice` 或其他未知分类货物合并。运行时沿用相同分类兜底规则。
- 没有有效货物 ID 的内部 CargoGood.NONE 是哨兵，不是可购买货物。它与 `my_pack:none/unknown` 这种真实、具备定义的货物不同。
- 容器、制造商、贸易点产出/需求/生产输入、商店中的悬空货物引用会拒绝新数据集合；删除货物必须同时移除引用。跨系统引用在货物加载 prepare 阶段校验，避免先发布货物目录再发现关联错误。
- 登录和成功 /reload 时向客户端分块同步完整货物名称目录；最终分块到达后一次替换。退出服务器时清空缓存，删除货物不会残留旧名称。
- 现存货柜保留创建时的容器兼容性快照，数据包新增货物不会自动赋予旧货柜新的兼容性。测试新货物应制造已配置兼容性的新货柜。
- 现存已装载 CargoGoodSnapshot 保留原始事实；其定义被删除后仍可显示/持久化货柜，但禁止继续装卸交易，不直接清空玩家货物。

## 5. 运行时与版本

```text
CargoContainerInstance
├─ Equipment
│  └─ CargoCompatibility[] { GoodId: 完整 CargoGood ID, Capacity }
└─ Load（空柜省略）
   ├─ Good { GoodId, DisplayName, UnitMass, BaseValuePerUnit, ... }
   ├─ 数量、完整度、运输词条状态
   └─ 结算币种、购入成本、装载时间、有效状态
```

CargoGoodSnapshot.cargoClass() 从保存的完整 GoodId 推导，读档无需实时货物目录。经济和库存以完整 ID 为键，不截去命名空间、不以 CargoClass 聚合。

| 项目 | 新版本 |
| --- | --- |
| 货柜 SavedData | 4 |
| 货柜条目 FormatVersion | 4 |
| 贸易点 SavedData | 7 |
| 货柜显示快照 | 2 |
| 客户端贸易点地图标记缓存 | 4 |
| 网络协议 | 9 |

沿用项目的无旧格式兼容策略，不迁移旧存档。开发测试请使用新存档或备份后的测试存档；本次改动不直接操作任何已有世界文件。

结构模板中的占位方块资源 ID cargoverse:cargo_type_decal_marker 暂时保留，以免破坏 NBT 模板；其 Java 类为 CargoClassDecalMarkerBlock，模型引用新版 none 图标。该资源名不再关联旧图标。模板中的静态 agriculture/none 贴花使用同名新分类资源，已校验无已删除贴花引用。
