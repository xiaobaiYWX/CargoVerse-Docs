## 1. 定位

货物定义描述一个具体 CargoGood 每货物单位的固有属性。所属 CargoClass 由文件路径首段确定，CargoClass 只管理一级分类和贴花，不决定价格、库存或兼容性。

货物单位的玩家可见缩写统一为小写 `t`，`1` 个货物单位显示为 `1t`。`t` 是本项目的货物计量单位；存档、数据包与代码内部仍使用原有 `units` 数值字段，不因显示缩写而改变数据结构。

货物定义负责：

- 科技等级与生产线匹配标签。
- 单位质量。
- 单位基础价值。
- 装卸该货物时使用的交易货币组。
- 单位运输许可证经验。
- 单位贸易点繁荣度经验。
- 新货物的基础完整度。
- 固有运输要求和词条参数。

货物定义不负责：

- 一个地点当前的市场价。
- 市场向玩家出售或从玩家收购的价差。
- 贸易点的库存、需求、产出或生产配方。
- 货柜容器能否运输该货物。
- 玩家当前持有的货物数量和完整度。

## 2. 文件位置

```text
data/<namespace>/cargo_goods/<class>/<good>.json
```

示例：

```text
data/cargoverse/cargo_goods/electronics/electronics.json
    → cargoverse:electronics/electronics

data/cargoverse/cargo_goods/mechanical_parts/create_mechanism.json
    → cargoverse:mechanical_parts/create_mechanism
```

路径严格为两段：第一段按硬编码 CargoClass 解析，未知分类统一回退到 `none`，不会注册新分类，也不会拒绝加载或改写货物完整 ID；第二段是数据包可新增的货物名称，不允许再嵌套子目录。JSON 不重复声明 ID 或分类。例如 `addon:future/ore` 的分类为 `none`，货物 ID 仍为 `addon:future/ore`，不会与 `addon:none/ore` 合并。

## 3. 完整示例

```json
{
  "schema_version": 1,
  "display_name": "电子设备",
  "tech_level": 2,
  "tags": [],
  "trade_currency": "cargoverse:enderite",
  "unit_mass": 1.0,
  "base_value": 70,
  "license_experience_per_unit": 3.5,
  "prosperity_experience_per_unit": 3.0,
  "base_integrity": 100.0,
  "transport_requirements": [
    {
      "id": "cargoverse:moisture_proof",
      "damage_per_second": 2.0
    },
    {
      "id": "cargoverse:fragile",
      "speed_delta_threshold": 10.0,
      "damage_amount": 5.0
    }
  ]
}
```

上述数值只用于说明格式，不代表最终平衡数值。

## 4. 字段说明

| 字段 | 类型 | 必填 | 约束 | 说明 |
| --- | --- | :---: | --- | --- |
| `schema_version` | 整数 | 是 | 当前为 `1` | 货物定义格式版本。 |
| `display_name` | 字符串 | 是 | 非空、最长 256 字符 | 直接显示文本，不支持 translate / text 对象。 |
| `tech_level` | 整数 | 是 | 0 至 2147483647 | 货物科技等级，供后续生产线定义使用。 |
| `tags` | 字符串数组 | 否 | 默认 []；禁止空白、重复及非字符串元素 | 普通语义标签，无需货物 ID 或 Minecraft 标签注册。 |
| `trade_currency` | 资源 ID | 是 | 必须指向已成功加载的货币组 | 贸易点装载和卸载该货物时使用的交易货币组。 |
| `unit_mass` | 数字 | 是 | 有限且 `>= 0` | 一个货物单位增加的物理质量。 |
| `base_value` | 整数 | 是 | `>= 0` | 一个货物单位的唯一基准价值。 |
| `license_experience_per_unit` | 数字 | 是 | 有限且 `>= 0` | 每成功交付一单位货物的基础许可证经验。 |
| `prosperity_experience_per_unit` | 数字 | 是 | 有限且 `>= 0` | 每交付一单位货物的基础贸易点繁荣度经验。 |
| `base_integrity` | 数字 | 是 | 有限且 `> 0` | 新装载货物的最大完整度。 |
| `transport_requirements` | 对象数组 | 否 | 默认 `[]`，最多 5 项 | 货物固有的运输要求，结构与词条定义一致。 |

## 5. 单位数值

货物所有经济和质量字段都改为“每货物单位”，不再乘以货柜 S、M、L、X 或 XL 规格价格倍率。

```text
货物质量 = unit_mass × amount

本批货物基准价值 = base_value × amount

基础许可证经验 =
license_experience_per_unit × amount

基础繁荣度经验 =
prosperity_experience_per_unit × amount
```

经验字段使用小数，在整批货物结算完成后统一四舍五入为整数。这样可以表示每单位 `0.8` 经验等数值，不会在拆分旧的整柜经验时丢失精度。

## 6. 基础价值

`base_value` 不分为基础买入价和基础卖出价。它是所有贸易点估值的统一锚点。

```text
当地市场价 =
base_value
× 贸易点本地价格修正
× 当前动态经济修正
```

市场出售加价、市场收购折价、事件修正和制造商声望都不写入货物定义。

## 7. 交易货币

`trade_currency` 必须引用数据包 `data/<namespace>/currency_groups/<path>.json` 中成功加载的货币组，而不是普通物品 ID。字段缺失、资源 ID 格式无效或目标货币组不存在时，整套货物数据拒绝生效。

首次向空货柜装载货物时，交易使用货物定义中的 `trade_currency`，并将其固化到装载运行时数据的 `settlement_currency_id`。同类型货物续装和之后卸载时继续使用该快照，避免数据包热重载在同一批货物运输途中改变结算币种。

## 8. 完整度

`base_integrity` 是新货物的最大完整度，实例中另行保存当前完整度。

同类型货物追加到同一个货柜时，完整度按数量加权合并：

```text
合并完整度 =
(原数量 × 原完整度 + 新数量 × 新完整度)
÷ (原数量 + 新数量)
```

禁止使用不考虑数量的简单平均。

若两批货物来自不同定义快照版本，在数据迁移规则未确定前不允许合并。

## 9. 运输要求

`transport_requirements` 使用当前词条系统的完整参数对象：

```json
{
  "transport_requirements": [
    {
      "id": "cargoverse:time_limit",
      "time_tick": 24000
    },
    {
      "id": "cargoverse:cold_chain",
      "damage_per_second": 1.0
    }
  ]
}
```

运输要求是货物的固有属性，但最终运行词条要在装载时结合制造商和具体货柜的特殊设计、设计缺陷重新解析。

## 10. 科技等级与标签

当前内置 20 个测试物统一暂填 tech_level 为 2，不代表最终科技分级。为接通默认贸易点生产链，化工原料的 tags 为 ["fertilizer"]、能源原料为 ["energy"]，其余暂为空数组。未来可按货物具体用途修改，例如精密构件使用：

```json
{
  "tech_level": 2,
  "tags": [
    "mechanical_part",
    "create_component",
    "precision_component",
    "industrial_component"
  ]
}
```

以上是字段片段，不是完整货物文件。标签去除首尾空白，区分大小写，运行时保存为不可变集合，不依赖顺序。代码可通过 CargoGoodDefinition.techLevel() 和 tags() 查询。

两者目前仅作为生产线可读取的定义元数据，不改变价格、货柜兼容性、许可证门槛、运输词条或交易逻辑，也不额外写入货柜装载快照。

[生产线池定义](17_生产线池定义.md) 已接入这两个字段的候选筛选：`all` 要求标签集合完全一致，`any` 要求标签存在交集，空标签条件不限制标签；科技等级同时必须落在 selector 的闭区间内。此筛选不改变货物自身的科技等级和标签。

实际数据包使用标准 JSON，不写解释性注释，也不添加注释解析逻辑。schema_version 仍为 1；缺少 tech_level 的外部数据包需补齐，货柜存档格式不变。
