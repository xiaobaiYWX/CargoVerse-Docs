# 物品货物转换与分类规则重构

工程对照、风险边界与分阶段实施建议见[货物系统重构工程方案](货物系统重构工程方案.md)。该方案同样待确认，不替代本文的需求方向，也不表示相关功能已实现。

> **待实现 · 设计草案 · 2026-10-19**
>
> 本文整理物品与货物接轨的讨论，不代表现行代码或数据格式。玩家贸易点已有实现；打包、解包及本文中的分类方案属于拟议扩展。已确认全仓共享 5000、损耗直接扣数量及破坏性重构不做旧档迁移；其余字段、数值和首版范围按下文继续确认。

> 范围补充：货物来源还包括流体、实体及后续扩展内容。本文保留原文件路径便于维护，但整体设计不再限定为物品转换；物品分类清单只是其中一个分支。

## 1. 问题与目标

现有货物系统通过贸易点的地域性供需，建立了长途运输需求，但货物与普通物品相互隔离，使原版生产、Create 自动化、制造与遗迹战利品难以参与运输经济。

新的方向是让普通物品能够成为物理货柜中的货物，并在目的地恢复为原物品。玩家工厂既可以为贸易网络供应货物，也可以从贸易网络获得生产资料。自然贸易点继续承担区域供需的作用，避免每个地区都能提供和收购全部商品。

需要同时解决两个问题：

- **兼容范围：** 不为每一种物品手工创建 CargoGood，再逐个编写转换配方。
- **运输动机：** 避免在供货站旁立即解包、通过背包搬运，再在收货站旁打包，从而绕过物理货柜运输。

本轮不恢复特殊订单或材料转化生产线，也不重新制定货物质量、价格、容量等具体数值。

## 3. 按内容类型组织转换流程

整体流程为“来源内容 → 对应类型的装载设备 → 物理货柜载荷 → 运输／交易 → 对应类型的卸出设备 → 恢复内容”。物品分支示例如下：

```text
普通物品
  → 玩家贸易点范围内的打包机
  → 解析分类与基础数据，记录原物品及数量
  → 写入对应物理货柜的货物载荷
  → 物理运输／贸易交接
  → 目的地玩家贸易点范围内的解包机
  → 恢复对应物品
```

自然贸易点与玩家贸易点之间仍可直接交易货柜中的货物，不要求每次交易都先解包。

打包是运输形态转换，不是制造配方。铁锭打包后仍应能够还原为铁锭；同属一个分类的铜锭、铁锭和模组金属锭不能因此互相转换。真正改变物品种类的加工应由其他明确的生产机制承担。

货物身份应从实际物品生成，分类只提供共享规则。新加入的模组物品即使没有专门配置，也应能进入默认分类；是否允许特殊物品打包，可另设明确的例外规则。

### 3.1 内容类型与运输属性分类

需要区分两个层次，不能把流体、实体直接加入现有物品分类清单后便认为完成兼容：

- **内容类型：** 决定如何读取、保存和恢复载荷，以及需要什么输入输出方式。例如物品、流体、实体。
- **运输属性分类：** 在一种内容类型内部提供共享运输属性。例如物品中的金属材料、流体中的普通液体或需特殊储运的液体。分类名称与属性尚未定案。

建议先识别设备所处理的内容类型，再在该类型内匹配分类清单与默认数据。各类型分别维护归属和默认值；物品 ID、流体 ID、实体类型 ID 不混入一份无类型清单。物品标签方案仅适用于物品分支，其他分支按自身可用的标识与标签设计。

| 内容类型 | 需要保存的内容 | 计量与还原边界 | 专用设备示意，名称待定 |
| --- | --- | --- | --- |
| 物品 | 物品 ID、整数个数、必要组件状态 | 还原为对应物品，检查输出空间 | 物品打包机／物品解包机 |
| 流体 | 流体标识、整数基础量、必要附加状态 | 按确定的流体单位守恒，检查接收储罐容量与流体兼容 | 流体灌装机／流体卸液机 |
| 实体 | 实体类型、逐个实例的必要状态及关联信息 | 按个体转移，在有效空间恢复；不能仅保存类型和数量后生成默认实体 | 实体装载设施／实体释放设施 |
| 其他扩展内容 | 由该类型明确规定的载荷与保存方式 | 必须定义可验证的输入、计量和恢复语义后才支持 | 按内容设计专用设备 |

物品形式的水桶仍属于物品载荷；直接从储罐抽取的水属于流体载荷。装有生物的物品也不自动等同于直接运输实体。两者之间若要转换，需要设备明确支持该行为，并处理容器返还等规则，不能由分类隐式完成。

默认分类只覆盖**已经支持的内容类型**中未被细分的内容。未知内容类型不能退回普通物品类型尝试解包。实体类型还需要明确允许运输的范围，不能因存在默认分类就开放所有实体。

### 3.2 设备分工与共享边界

允许不同类型具有不同的功能方块、交互界面、输入输出口、处理时间与配套空间。无需让物品打包机处理管道流体或捕获实体，也不要求每个贸易点具备全部类型的转换设施。

各设备应复用玩家贸易点绑定、权限、物理货柜识别和转移结果确认等共同机制；内容的读取、保存、恢复与适配校验由对应类型负责。货柜可以声明支持的内容类型及分类限制，例如液体储运柜或实体运输柜；已有货柜系列如何对应，另行设计。

转换前需要同时满足设备支持、货柜兼容和目的地可接收等条件。输出空间不足、储罐不兼容或实体无法安全放置时，应保留尚未转移的载荷，不能先清空货柜再尝试输出。若支持分批转移，仅扣除已成功转移的部分。

实体分支还需专门确定存活状态、年龄、驯服与归属、装备、乘骑关联和身份标识等保存策略，以及运输期间是否推进其状态。装载与释放必须保证个体不会重复存在；这不是简单把物品堆叠逻辑换成实体 ID 即可完成的兼容。

以上是设计边界，不意味着首版必须同时完成所有分支。可以先实现物品转换，但公共货柜与交易设计应能明确区分内容类型，后续流体、实体通过各自设备接入。

## 4. 通过玩家贸易点约束转换位置

### 4.1 已确认的使用条件

- 打包机、解包机绑定一个有效的玩家贸易点，复用现有权限与生命周期机制。
- 设备与绑定点位于同一维度，并处于规定的实际作用范围内；仅填写贸易点 ID 不应获得远程使用能力。
- 玩家拥有或获授权使用该贸易点；自然贸易点不自动成为玩家设备的通用绑定对象。
- 按所有者 UUID 跨维度统计玩家贸易点，默认最多 1 个，可在配置文件修改；区块卸载、暂停营业仍计数，授权管理者不额外提供名额。
- 所有玩家贸易点终端和功能方块可以正常放置在 Sable 结构上，但不能绑定和使用，并显示原因提示，包括核心、公共/管理终端及区域标记杆；不是仅暂停打包/解包。不阻止放置/组装，也不禁止货柜本身在物理结构中被运输及装卸。
- 转换设备为可选多台设备，沿用 32 格绑定及管理权限，不要求贸易点对公众营业；转换使用设备缓冲和区域内单货柜，不强制经过仓库，不收费且不产生交易经验。

这里的打包、解包统称包含流体灌装卸出、实体装载释放等转换行为。专用设备仍受同一套节点约束，不能通过更换设备类型绕过绑定限制。

这些限制旨在让基地、工厂与物流节点相对固定。它们不能证明物品实际在哪里生产，也不应被描述为能强制所有农场和机器集中在节点范围内。玩家从外围生产设施把物品送入自己的打包中心，仍是合理玩法。

### 4.2 防频繁拆装：留待后续设计

仅限制同时存在的贸易点数量，还不足以阻止玩家反复拆除、重建临时节点。用户明确本轮不添加拆除后冷却或创建费用，实际拆除核心释放名额后可立即在额度内重建；防频繁拆装后续另行设计，可能引入 VB 创建成本，但不属于本轮范围。

需要区分两类行为：

- 长期把基地建在某个贸易点附近，获得当地运输便利：可以接受的区位选择。
- 每次采购或交货时临时建立转换点，完成转换后立刻拆除：会削弱运输约束，记录为后续设计问题，不作为本轮必须封堵的行为。

设备绑定范围 32 格、每名所有者默认 1 个且可配置，以及所有设施在 Sable 上可放置但不能绑定/使用并提示已确定；本轮明确无建点冷却或创建费用，不添加未使用的迁移约束框架。本方案不承诺消除背包、潜影盒或临时重建等所有绕行方式。

## 5. 货物载荷与分类数据分离

| 数据层 | 负责内容 | 不应承担的职责 |
| --- | --- | --- |
| 内容类型 | 指明载荷解释方式、对应处理能力与计量语义 | 代替具体运输属性分类 |
| 原始内容载荷 | 按类型保存实际物品、流体或实体及还原所需状态 | 推断市场价格或改写内容身份 |
| 分类基础数据 | 为同类物品提供运输属性默认值 | 把同类物品合并成可互换的抽象商品 |
| 分类归属清单 | 决定物品适用哪个分类 | 逐件保存运输中的物品状态 |
| 贸易表 | 决定站点收售什么、价格与交易限额 | 决定一个物品是否能够被打包运输 |

**不使用耐久、饱食度、附魔、挖掘等级等属性进行分类，不等于打包时丢弃这些状态。** 解包要还原原物品，就必须保存必要的物品组件数据；这属于载荷保存，不属于分类推断。

同一物品 ID 下具有不同状态的物品，不能无条件混为一个条目。用户已确认首版每柜只承载同一种物品、同一种完整组件状态，不允许非空嵌套容器；混装以后另做。

实际物品数量以整数保存。已确认 1 个实际物品 = 1 库存单位 = 1 货柜容量单位，质量另算，不按物品栈换算；物品数量不再显示为 `t`。未受损的转换严格守恒，运输损耗明确扣数量，不能在普通换算时丢失或增加物品。

流体基础量、实体个体数同样应有各自明确的计量规则，不强行套用“一个物品等于多少货物”的比例。公共运输层可以使用各类型计算出的占用与质量等结果，但不能丢弃原始计量单位，也不能把不同类型的载荷仅按同一个 `t` 数值相互替换。

## 6. 分类方案比较

本节比较针对物品分支。其他内容类型可以沿用“分类基础数据、归属清单、默认值”的组织思路，但不要求沿用物品标签、载荷字段或计量方式。

| 方案 | 优点 | 主要代价 | 本文建议 |
| --- | --- | --- | --- |
| 只根据原版与通用标签自动分类 | 对遵循标签约定的物品可批量兼容 | 标签覆盖不完整，语义交叉，也不直接表达运输属性 | 可作为辅助，不能承担全部归类 |
| 分类基础数据 + 物品 ID 清单 + 默认分类 | 结果可控，易于审查，未知物品也有兜底 | 需要维护常用物品与模组兼容清单 | 作为首版基础 |
| 自定义分类标签，清单内允许引用已有标签 | 同时支持精确列举与批量纳入，复用数据包机制 | 仍需处理重叠归属和标签变更 | 建议作为上述清单的承载方式 |
| 根据注册名、名称关键词或模组名推断 | 初期配置少 | 命名不保证语义，误判难解释 | 不作为正式分类依据 |
| 分析配方、物品组件或其他属性推算 | 可表达更多差异 | 规则复杂，与本轮只做基础分类的范围不符 | 暂不采用 |

建议采用的是一套分类流程，而不是多套并行的规则引擎：作者维护归属清单，系统解析清单，再为物品生成对应的运行数据。

### 6.1 推荐的归属清单形式

可使用 CargoVerse 自定义物品标签作为清单，既允许填写精确 ID，也允许引用经过作者确认的已有物品标签。

例如，下面仅演示一个候选分类标签 `cargoverse:cargo_categories/metal_materials` 的写法，不是已落地资源或最终分类定义：

```json
{
  "replace": false,
  "values": [
    "#c:ingots",
    "#c:nuggets",
    "minecraft:netherite_scrap"
  ]
}
```

引用 `#c:ingots` 表示作者明确同意将该标签中的物品批量纳入。它不意味着系统会扫描所有标签名称并猜测分类，也不意味着所有金属制品自动获得相同数据。

分类的运输数据独立定义，不写入标签 JSON。已确认保留现有 CargoClass 的货柜兼容、分类容量与贴花用途，但删除由商品 ID 路径推导分类的规则；具体字段、数值和目录在数据定义时落实。

### 6.2 匹配、冲突与兜底

建议首版采用简单、可解释的规则：

1. 解析自定义分类清单及其中引用的标签。
2. 恰好匹配一个分类时，使用该分类的基础数据。
3. 没有匹配时，使用默认分类，并允许作者查看未分类物品列表。
4. 匹配多个分类时，报告冲突及来源，不能由文件遍历顺序静默决定结果。

已确认冲突拒绝本次新快照并列出来源；重载时保留上一代有效配置，首次加载没有有效配置则明确报错，不发布半套规则。不加入复杂的优先级、继承和逐字段合并机制。

需要更细的物品例外时，优先修订清单或调整分类边界。独立的逐物品属性覆盖表属于可选扩展，不作为首版必需内容。

## 7. 原版与通用标签的使用边界

物品注册 ID 是识别物品的基础，但原版 `minecraft:` 物品标签和通用 `c:` 物品标签并非每个物品都必须具备。一个物品可能没有标签，也可能同时属于多个标签；模组是否正确提供通用标签同样取决于其实现。

可优先考虑引用以下语义较明确的标签族。它们是归属清单的候选来源，不是最终运输分类表：

| 候选归类领域 | 标签示例 |
| --- | --- |
| 矿产与金属原料 | `c:ores`、`c:raw_materials`、`c:ingots`、`c:nuggets`、`c:gems`、`c:dusts` |
| 木材与植物原料 | `minecraft:logs`、`minecraft:planks`、`minecraft:saplings`、`minecraft:leaves` |
| 农作物与食品 | `c:crops`、`c:seeds`、`c:foods` 及其细分标签 |
| 纤维与动物材料 | `minecraft:wool`、`c:strings`、`c:leathers`、`c:bones`、`c:feathers` |
| 石材与建筑材料 | `c:stones`、`c:cobblestones`、`c:sands`、`c:glass_blocks`、`minecraft:terracotta` |
| 工具与装备 | `c:tools`、`c:armors`、`minecraft:pickaxes` 等 |

其中部分标签在特定安装环境中可能为空。方块标签也不能直接当作对应物品标签使用。染色、可附魔、游戏行为等标签未必适合决定运输分类。

因此，通用标签适合降低清单维护量；**精确 ID 与默认分类仍然是兼容完整性的保障。** 本文不以标签数量或覆盖比例替代实际分类设计，也不要求对所有模组物品逐项适配后才能使用打包功能。

标签机制参考：[NeoForge 1.21.1 官方标签文档](https://docs.neoforged.net/docs/1.21.1/resources/server/tags/)。

## 8. 与贸易网络及现有数据的关系

能够打包不等于自然贸易点必须收购。默认分类提供运输基础数据，不应自动赋予 NPC 收购价格或全站交易权限。

贸易选择条件还应区分内容类型与具体内容。相同显示名称或相近分类不能让流体、盛装流体的物品、实体或装有实体的物品相互代替交货。站点的交易支持范围与装卸设施也需要匹配；具体如何扩展贸易表暂不在本草案中定字段。

自然贸易点需要继续按地区与职责区分供应、需求、库存及交易限额。限制本地消化能力，可以让玩家工厂存在向外运输的理由；但具体是否调整既有大站收购策略，应另做经济设计，不能因本草案直接恢复收购库存或统一修改上限。

玩家贸易点沿用现有的实际库存、资金、报价与权限体系。新增转换设备应接入这些边界，不另造一套经营账户或交易结算系统。

库存上限的补充方向已明确：整个玩家贸易点仓库共享 5000 个实际物品的额度，不同物品、组件变体及批次共同占用，不再逐商品提供 5000。后续如需增加容量，再专项设计仓库扩容器。实际入库同时受到共享余量与商品收购目标限制，目标不代表预留仓位。

用户已确认完整度采用方案 2 重构：词条每次扣固定整数个物品，不按百分比；例如原撞击扣 10 点完整度对应新扣 10 个，100 → 90 → 80。持续损耗按间隔扣整数数量，不累计小数损耗，也不在卸货时补扣。仓库与交易只处理实际剩余数量，不生成损坏货物副产物；旧平均完整度、完整度折价及最低收购完整度门槛随重构清理。

时限规则保留：保护期结束后，每隔一段时间扣固定数量；成功追加实际货物允许刷新保护期，理解为补充冷却介质。它不使整批瞬间失效、不恢复已扣物品，也不要求原物品携带终身到期时间。已确认使用游戏 tick、停服不推进、区块卸载推进并在加载时补算；保护期结束后经过一个扣量间隔首次扣货，追加先结算旧周期再刷新，部分卸货不刷新。详见[工程方案第 8 节](货物系统重构工程方案.md#83-时限)。

用户已确认开发阶段按破坏性重构实施，不做旧货柜、仓库或存档迁移，不编写旧商品兑换表或保留旧格式兼容链。新格式仍需正确保存资产并保护异常数据；不迁移不等于立即删除世界文件。新玩法中仍需明确：

- 现有货物哪些可以对应真实物品，哪些作为世界观特殊货物保留，哪些需要淘汰。
- 贸易表如何选择物品或物品集合，以及如何区分不同组件状态。
- 新货柜、玩家仓库与真实物品如何一致保存，避免新格式数据丢失或重复兑现。
- 显示名称、图标与客户端同步如何使用实际物品信息。

这些问题尚未定案。不能默认把旧货物直接按名称兑换为物品，也不能继续要求每种可运输物品必须先有一份独立 CargoGood。

## 9. 后续设计顺序与验证目标

建议先确认首版范围、计量与物品身份，再确定分类及默认数据、损耗细则和节点限制，最后重做贸易网络的商品选择和经济数值。不安排旧数据迁移阶段，避免先批量重写货物清单后又因载荷模型变化返工。

进入实现前仍需确定：

- 各分类的具体质量与词条配置；分类规则及保留 CargoClass 的兼容、容量和贴花用途已确认。
- 物品专用设备、货柜兼容及默认分类范围；首版仅物品已确认。
- 流体计量与储罐接口、实体允许清单与状态保存留待各自专项，不作为首版阻塞项。
- 完整组件身份与非空嵌套容器的识别细节；不混装已确认。
- 玩家贸易点配额主体、默认数量、设备作用范围和设施在 Sable 上可放置但不能绑定/使用并提示已确认；拆除冷却和未来可能的 VB 创建成本不在本轮范围。
- 固定整数扣量、时限后周期扣货、补货刷新及游戏时间/区块卸载补算等边界均已确认，实现时落实一致的扣量时钟。
- 已确认在途货物使用装载时的运输快照；落实重载及不兼容快照禁止追加的校验。
- 新格式下缺失模组物品时的保护行为；旧档不迁移已确认，不再作为待选项。

验证目标包括：

- 常规物品和没有专门适配的模组物品均有明确分类结果或默认结果。
- 未发生运输损耗时，打包与解包保持物品 ID、数量和必要状态；重复操作不产生物品。
- 同类但不同 ID 的物品不因归类发生互换；冲突可被作者定位。
- 分类规则更新不改写载荷中的原物品身份。
- 未绑定、超出范围或无权限的设备不能完成转换。
- 物品兼容范围扩大后，贸易点仍保持各自的供需范围，不变成万能市场。
- 设备与货柜只处理声明支持的内容类型，未知类型不会被错误套用物品默认值。
- 流体转移按基础量守恒，实体转移保持个体状态且不重复生成；输出受阻时保留未转移载荷。
- 各类型专用设备遵守相同的贸易点绑定与权限约束，但不要求共用界面或输入输出形式。
