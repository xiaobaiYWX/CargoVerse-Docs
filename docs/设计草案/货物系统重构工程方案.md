# 货物系统重构：工程复核与实施规划

> **设计评审建议 · 待确认 · 2026-10-19**
>
> 对照当前代码复核[物品货物转换与分类规则重构](物品货物转换与分类规则重构.md)。本文不是现行格式；已确认决策与待确认建议分列，不能把未确认建议视为最终玩法。本轮只整理设计与实施顺序，不修改业务代码。流体、实体属于总体设计边界，不因列入本文而承诺首版实现。

## 1. 结论与首版边界

方向可行，但不能仅在现有 `CargoGood` 上增加一个物品 ID 字段。建议保留货柜资产和物理运行时，把目前耦合在一起的三件事拆开：

1. **内容身份**：柜内究竟是什么，原始数量和组件状态是什么。
2. **运输规则**：占用容量、单位质量、货柜兼容性以及运输要求。
3. **交易规则**：哪些贸易点可以买卖、价格、收购目标、保留数量和经验。

首版范围已确认：只打通普通物品的完整闭环，物品输入 → 打包 → 货柜 → 装卸交易或仓库 → 解包输出。每柜只存一个物品 ID 和一种完整组件状态，不混装；首版不允许非空嵌套容器。暂不实现流体、实体转换，也不为它们提前建立空适配层。

继续保留以下既有边界：

- 公共装载、卸载终端始终正常计价，所有者和管理员不享受免费交易。
- 仓库管理终端承担授权管理者的免费仓库装卸，不与公共交易混合。
- 核心终端、授权名单、连接器绑定与解绑依然仅限所有者。
- 新转换设备使用已有玩家贸易点连接和管理权限体系，建议作为**可选设备**，不增加贸易点开业的必须终端。
- 不恢复生产线终端、货柜机械台、虚空混合物流体或已删除的无功能终端。

## 2. 当前实现与需要变化的地方

以下路径均相对于代码工程 `CargoVerse-NeoForge-1.21.1/src/main/java/cn/or15/cargoverse/`。

| 当前入口 | 现状 | 重构影响 |
| --- | --- | --- |
| `trade/CargoGood.java` | 商品 ID 必须有路径分隔符，分类来自路径首段 | `minecraft:iron_ingot` 不能直接放进这个字段，否则会被判为无效；内容身份必须独立 |
| `cargo/CargoGoodSnapshot.java` | 混合名称、质量、价格、经验和运输词条快照 | 拆开运输快照和交易定义，避免可运输物品必须填写价格 |
| `cargo/CargoLoad.java` | 单一商品、整数数量、完整度、词条运行状态和购入成本 | 继续单载荷，但增加真实内容及其批次状态，不能只保存物品 ID |
| `cargo/CargoContainerSnapshot.java` | 兼容性与容量按商品路径推导出的 `CargoClass` 决定 | 改为显式运输分类；另行判断是否支持该内容类型 |
| `trade/CargoLoadAssembler.java` | 追加货物时会按当前定义重新构造快照 | 明确追加批次兼容条件，不能在重载后悄悄重写旧货物的运输属性 |
| `playertrade/PlayerTradeListing.java` | 同一记录同时承担库存、平均完整度和报价配置，单行上限 5000 | 库存与交易设置拆开，全仓共享容量；删除平均完整度及其设置/显示 |
| `playertrade/PlayerTradeWarehouseInventory.java` | 按商品 ID 保存一个库存行，不存物品组件及完整批次状态 | 直接沿用会丢失物品变体、运输时限和损耗来源 |
| `trade/resource/ResourceTableDefinition.java` | 自然贸易表显式引用商品，出售库存使用双精度数量 | 真实物品流转改为整数账本；默认运输分类不自动进入收购表 |
| `cargo/data/CargoDataReloadListener.java` | 多类定义集中校验与替换，已有一致性快照入口 | 复用入口；分类标签必须在服务端标签可用后编译并一致发布 |
| `cargo/data/CargoGoodCatalogSync.java` | 登录、重载同步静态商品名称和图标 | 不应扩展为同步全注册表及所有组件组合 |
| `cargo/CargoContainerInstanceCodec.java` | 实例格式版本 6，支持部分旧版 | 本轮切换不兼容新格式，删除旧版解码分支；新格式未知内容或缺少模组不能解码成空柜 |

本轮文件核对有 **108 个货物定义、60 个货柜定义**。当前这 60 个货柜均未显式允许 `none` 分类，所以“未配置物品使用默认分类”还需要同步设计默认货柜兼容性，不能只返回 `none` 就认为能够装载。数量仅记录本次核对结果，不作为长期固定常量。

### 可以直接复用的部分

货柜 UUID、归属、实体设备与载荷分离、Sable 物理身份、终端连接、单货柜识别、权限验证、货币账本及地图交易摘要可以继续使用，只调整其数据接口。无需为本轮重构重新建立这些系统。

现有制造平台已经使用物品及标签作为制造成本，适合参考其匹配和校验方式；它负责制造货柜，不应重新兼任打包机。普通物品商店也不因本轮重构自动合并进货物市场。

## 3. 建议的数据职责

本节是职责约定，不是最终 Java 类型或 JSON 字段。

### 3.1 内容身份与数量

物品载荷保留以下内容：物品注册 ID、一份数量为 1 的完整组件模板、独立的整数总数量。数量不受单个 `ItemStack` 最大堆叠数限制；解包时再拆成合法物品栈。

组件包含名称、附魔、耐久等原始状态。身份比较必须比较真实组件，不能只按显示名、标签或哈希值判断相等。哈希只做索引；模板应复制保存，不能引用外部可变物品栈。

建议数量账本使用有界整数，必要时用 `long` 保存原始物品数；加减乘除执行溢出检查，超限拒绝操作，不用饱和加法吞掉超出数量。向现有整数容量或显示字段转换前校验范围。

不强制流体或实体以后使用同一模板、单位或内部数据结构。共享的只是“识别内容类型 → 定位货柜 → 校验 → 提交载荷变化”的外层边界。

### 3.2 运输分类与默认规则

- 已确认保留现有 `CargoClass` 作为首版货柜兼容类别、分类容量及贴花的轴，不再从物品 ID 路径推导。
- 新运输配置独立保存类别、单位质量和运输要求，物品标签只负责分配配置。已确认一个物品占一个容量单位，不再引入逐物品空间权重。
- 一个物品命中多个不同配置时视为冲突，给出物品 ID、规则和标签来源；不依赖文件顺序，不自动叠加字段。
- 未命中时使用明确的默认运输配置；哪些通用货柜接受它需要数据包显式声明。
- 分类只决定运输属性，不代表材料可互换，也不代表允许 NPC 交易。
- 标签解析和成员缓存集中在加载阶段完成，不在装卸 tick、GUI 绘制或每次价格计算时扫描全部物品。

分类配置和标签应编译成同一代不可变运行快照，校验后一次发布。重载失败保留上一代可用快照；首次启动没有可用定义时报告错误，不发布半套规则。具体标签生命周期接入点在实现时按项目 NeoForge 版本验证。

### 3.3 运输快照与批次状态

新载荷记录运输配置快照及版本；途中货物不随数据包重载改变质量、分类或运输要求。追加要求物品组件及运输快照一致；成功追加后允许刷新整个柜内载荷的时限保护期，不要求追加货物与原货物具有相同剩余时间。

不兼容的载荷拒绝追加。仓库不再为了平均完整度或小数损耗保存批次；GUI 仅汇总实际数量。时限是货柜运输状态，不是原物品终身年龄，不向原物品组件写入损耗或冷却时间。仓库的最终合并规则仍与第三批库存设计一起确认。

保留数量和收购目标继续是交易设置，不是实物库存，更不是货柜容量。改变设置不会生成、删除或转换物品。

### 3.4 市场与价格

建议保留一个**可选的市场商品定义目录**，仅为允许交易的内容定义基础价格和经验等经济参数。普通物品运输无需注册市场商品；自然贸易表继续显式引用目录并设置当地供需及倍率。

目录是经济身份，不再承担运输内容身份。玩家自行定价不必先创建 NPC 商品定义，但仍须匹配具体内容身份。

首版自然贸易建议只匹配标准组件状态的物品；耐久不同、附魔不同等变体必须有显式规则才可收购。否则会出现低品质物品按标准物品收购、再输出全新物品的问题。标签若用于市场清单，应展开为各物品独立条目，不允许同标签物品相互替代，也不共享实物库存。

当前自然贸易可配置无限出售。可解包后，这就等于无限真实生产资料来源；需要逐项审查开放清单、价格和供给规则，不能批量把全部旧货物映射成无限物品出售。本轮先定边界，不顺带重做全套经济数值。

## 4. 必须提前封住的漏洞与边界

### 4.1 数量、容量与质量不能继续混用

**计量已确认：1 个实际物品 = 1 库存单位，也占用 1 个货柜容量单位。** 不按堆叠数换算、不设置逐物品空间权重；货柜最大个数仍由货柜定义决定，质量按物品运输配置另算。物品页面不再使用 `t` 表示数量。

**已确认方向：整个玩家贸易点仓库共用 5000 个实际物品的上限，所有不同物品、组件变体和批次共同占用，不再为每种商品各提供 5000 容量。** 后续如需深化，再单独设计仓库扩容器，本轮不实现扩容器。该上限不是 5000 个物品栈槽位。

实际可入库量同时受“仓库剩余额度”和“该商品剩余收购目标”限制。保留数量和收购目标仍逐商品配置；允许设置的目标之和超过 5000，但这不是预留空间，实际入库按提交时的共享余量校验。例如仓库已有 4800，某商品还希望收购 1000，本次最多只能入库 200。管理装卸、公共收购、转换及其他写入路径使用同一个容量入口，不能只在 GUI 限制。

同时限制变体数和必要的批次数，避免零库存报价或大量小批次造成无界数据。本轮不迁移旧仓库，也不实现旧档超额兼容；新格式下多玩家或自动化并发入库必须在同一次提交中检查并占用共享额度。

### 4.2 损耗、时限与解包重置

**已确认：采用方案 2，运输损耗直接扣减货柜中的实际货物数量，替代独立完整度系统。** 不实现损坏货物副产物。下表只保留方案选择的比较依据，方案 1 不在本轮实现范围内。

| 方案 | 正常卸下的原物品 | 受损部分 | 主要代价 |
| --- | --- | --- | --- |
| 1：柜内完整度，卸货转换 | 100 木头、80% 完整度卸出 80 木头 | 另生成 20 个实际的损坏货物物品 | 要处理双产物、损坏货物的存储和质量，以及堵塞、部分卸货和处置用途 |
| 2：损耗直接扣数量 | 100 玻璃受损 10 个，柜内立即剩 90 个，卸出 90 个 | 默认作为运输消耗，不生成实体物品 | 要重构各词条的整数扣量、触发周期，以及损耗后实时质量变化 |

方案 2 让仓库、交易和解包遵守同一个真实剩余数量，不再在仓库延续“平均完整度”。损耗是显式消费，不要求损耗前后物品总数相等；未受损的转换、交易与拆分仍必须严格守恒。

按已确认的方案 2，需要一起修改：

- 词条只产生数量损失，不修改物品自身的耐久、附魔等组件；剩余物品保持原始状态。
- 交易按实际转移数量计价，不再乘完整度折扣；移除最低收购完整度门槛或另行设计，不能双重扣损。HUD 优先显示实际数量，不把“剩余数量/货柜容量”冒充完整度。
- 货柜载荷质量按实际剩余数量更新，柜体质量保持不变；损耗导致的载具减重是玩法变化，需要物理测试。
- 数量降为 0 后结束该载荷及其词条计时；不能留下只有失效状态、没有物品的幽灵货物。失效事件需明确是全部损失还是另有处置，不保留旧的“有数量但无法取出”旁路。
- 已确认按词条每次的固定扣量直接扣实际物品，例如易碎碰撞扣 10 点改为扣 10 个。不是按当前量或初始量的百分比计算；不足 10 个时扣完剩余数量，不出现负数。
- 持续损耗按“触发间隔 + 每次扣除整数数量”配置；保存时间进度，不保存小数物品损耗，不在卸货时向上补扣。旧的小数每秒伤害配置需要逐项重新制定为整数扣量与周期，不直接截断或机械放大。

不为方案 1 添加损坏货物注册、缓冲库存或回收用途。若以后引入废料玩法，另做专项设计。

时限已确认保留，重构为“保护期结束后，每隔一段时间扣固定数量”。成功追加实际货物允许刷新保护期，相当于补充冷却介质；这是允许的玩法，不作为要封堵的漏洞，也不额外要求未提出的介质物品成本。到期不标为不可卸出的失效载荷、不瞬间清空整批。时间边界与保存细节见第 8 节。

### 4.3 嵌套容器与不支持内容

带物品的容器、流体容器、实体容器和本模组货柜资产不能只靠外层物品重量安全处理，否则可以套娃绕过质量和容量。已确认首版不允许装有其他内容的嵌套容器；识别方式与禁用清单仍需落实，不能保证任意模组私有数据都可自动识别。不在未确认时自动为普通非空容器开放例外。

普通耐久或附魔状态不是禁用理由；与嵌套内容区分。未知或超出大小限制的组件应拒绝本次转换并保留输入，不截断组件、不回退成无组件物品。缺失物品注册、缺失模组或不认识的载荷类型保留原始数据并隔离，等待恢复，不变成空柜。

### 4.4 转换设备、权限与空间约束

已确认物品打包、解包设备分别实现自己的库存与转换逻辑，复用终端连接工具、玩家贸易点 32 格绑定范围和管理权限。一个核心可绑定多个可选转换设备，不要直接塞入当前每种必须终端只有一个位置的槽位。

设备需要有效核心、有效绑定和对应装卸区域，但不要求贸易点已向公众营业，避免把工厂物料转换与税费、公共终端齐备状态意外耦合。手动转换由所有者或获授权管理者操作；自动化通过设备受控库存口工作，服务端每次提交仍验证绑定与核心有效性。

玩家贸易点数量限制目前尚不存在，已确认重构时新增：按所有者 UUID 在全存档、跨维度计数，默认上限为 1，可由配置文件修改；已卸载区块和暂停营业的核心也占额度，授权管理者不增加名额。不要为计数强制加载所有核心区块。本轮不添加拆除后建点冷却、创建费用或防频繁拆装系统，不预留未使用的冷却运行时。

已确认玩家贸易点的所有终端及功能方块**允许正常放置在 Sable 结构上，但不允许绑定和使用**，交互时显示对应提示；不阻止方块放置或结构组装。核心、公共装卸终端、仓库管理、信息柜、航标、区域标记杆和新增转换设备全部属于该边界，结构静止也不例外。该限制针对玩家贸易点设施，不禁止其识别、交易和装卸 Sable 结构上的货柜，也不扩展到普通贸易点、载具仪表或其他无关方块。

### 4.5 转换一致性与崩溃恢复

建议先使用设备自有输入、输出缓冲区，按“预检 → 校验版本与绑定 → 提交 → 留存结果”处理；输出不够时保留剩余载荷，不先清空货柜。一次只操作一个货柜，同一设备串行执行，交互请求防重，自动化每步数量有上限。

外部物品处理器的模拟插入不等于原子事务，不能把任意模组接口都当成可以回滚的数据库。先让外部自动化只操作本设备缓冲，避免跨多个外部库存做伪事务。

设备方块实体与货柜 SavedData 分别存储，普通执行顺序不能保证异常断电时原子落盘。若要求崩溃后也严格防复制，需要设计可恢复操作记录与幂等提交，并实测不同保存顺序；不能仅加一个操作 ID 就宣称完全解决。首版至少对不确定的恢复状态隔离并报警，不盲目重放产出。

## 5. 存档与客户端

### 5.1 已确认：破坏性重构，不做旧存档迁移

当前货柜 SavedData 根版本是 4，实例格式版本是 6，仅作为旧实现审计记录。用户已明确开发期不要求存档迁移，本轮使用不兼容的新数据格式与网络协议，不维护旧 CargoGood 载荷、旧完整度或旧仓库的迁移器、兑换表及兼容解码链。

实施时直接修改调用方、数据包、测试、客户端显示与同步，最后删除被替代的旧代码和无引用资源，不以兼容包装层长期维持两套体系。旧商品设定是否仍用于新市场目录，按新玩法逐项重写；不因复用名称而保留旧载荷模型。

验证使用新建或用户明确允许重置的测试环境。不做迁移不等于现在删除世界文件，也不等于可以破坏新格式的资产保护；发现旧格式应明确报告不支持，新格式遇到缺失模组、未知组件或异常数据仍保留并隔离，不静默清空后覆盖存档。

### 5.2 网络与显示

模块应向 UI 提供有界摘要，不把完整载荷 NBT 广播给每个客户端。名称和物品渲染尽量使用客户端注册信息，组件变体只在需要的页面、交互详情中同步受限预览。

静态规则、库存页面和实时读数分开；不在每次库存变化时重发全部分类。客户端缓存键、货柜 HUD、终端选项、地图商品摘要、命令和图标解析统一改用新身份接口，禁止遗留路径推导分类的旁路。

物品数、变体数、批次数、组件大小和包大小都设上限，避免把“支持所有物品”实现成“预生成所有可能组件组合”。

## 6. 实施阶段与验收顺序

每一阶段都应保持可编译、可验证；单纯新增数据结构不算完成一个可发布的转换功能。

| 阶段 | 工作 | 进入下一阶段前必须证明 |
| --- | --- | --- |
| P0：冻结约定 | 确认首版范围、计量、损耗细则和建点限制；隔离工作区已有终端清理与重型接口改动 | 共享 5000、直接扣数量和不迁移已确定；其余约定完成确认，不混入无关改动 |
| P1：身份与规则 | 物品身份、完整组件、整数数量、分类编译、默认兼容、载荷解码与隔离 | 同名不同组件不合并；标签冲突可定位；坏数据不丢失；重载一致 |
| P2：货柜载荷 | 接入实例、容量、质量、追加及拆分、运输快照和批次状态 | 打包前后的物品量守恒；重载不改变途中货物；物理质量正确 |

### 最小验证矩阵

- 原版可堆叠物品、不可堆叠物品、带名称/附魔/耐久的物品；重复打包解包后逐项比较组件和数量。
- 同 ID 不同组件、相同标签不同 ID、跨规则重载的批次，确认不会互换或错误合并。
- 货柜部分取出、仓库拆批合批、装卸交易、5000 边界、整数溢出和空间不足。
- 管理员与所有者走公共交易正常收费；非授权者不能转换或越权改绑定。
- 输出满、设备/核心被移除、区块卸载、重复请求、玩家断线、不同存档保存时序下恢复。
- 缺失模组、未知载荷、异常组件和标签冲突；恢复后原数据仍可检查，不静默清空。
- 多玩家、多贸易点自动化压力下，确认没有逐 tick 全注册表扫描和无界批次同步。

## 7. 决策清单与确认顺序

### 7.1 用户已确认

1. 整个仓库共享 5000 库存限额，不同物品共同占用；扩容器后续另做。
2. 完整度系统以方案 2 为重构目标：损耗直接扣实际数量，不生成损坏货物副产物；旧完整度折价和平均完整度体系随之清理。
3. 按破坏性重构实施，不要求旧存档迁移，不添加旧格式兼容层。此项不代表立即开始业务实现或删除测试存档。
4. 首版仅完成物品闭环，流体、实体后续专项添加，本轮不编写空适配层。
5. 1 个实际物品 = 1 库存单位；仓库共 5000 个，货柜容量也以个数表达，质量独立计算，物品数量不再显示 `t`。
6. 每柜一个物品 ID、一种完整组件状态；名称、耐久、附魔等不同状态不混装；首版不允许装有其他内容的嵌套容器。
7. 分类采用共享运输配置、自定义标签清单和默认配置；冲突拒绝新快照，保留原分类的货柜兼容/容量/贴花作用，途中使用装载快照。
8. 词条每次扣固定整数个物品，不按百分比计算、不累计小数损耗、不在卸货时补扣尾数。
9. 时限保留为保护期结束后的周期固定扣量，追加实际货物可以刷新保护期；不引入物品终身年龄或独立完整度。
10. 时间使用服务器游戏 tick，停服不推进；区块卸载仍推进，加载或交互前补算。保护期结束再经过一个扣量间隔首次扣货；追加先结算旧周期再刷新，部分卸货不刷新。
11. 玩家贸易点所有终端和功能方块可正常放置在 Sable 结构上，但不能绑定和使用，操作时显示提示；不阻止放置或组装。货柜本身仍可作为物理运输对象。
12. 玩家贸易点按所有者 UUID 跨维度统一计数，默认最多 1 个，上限可在配置文件修改；区块卸载、暂停营业仍占名额。
13. 转换设备可选、允许多台，沿用 32 格绑定及管理权限，不依赖公众营业状态；自有缓冲直接与装卸区域单货柜交换，免费且不产生交易经验，不强制经过仓库。
14. 本轮不设核心拆除后的建点冷却，不收创建费用；防频繁拆装及未来可能的 VB 创建成本另行设计，不纳入本轮重构。

## 8. 第二批约定：分类、固定数量损耗与时限

分类规则及固定扣量、保护期后周期损耗、补货刷新和以下时间边界已由用户确认。原百分比、定点损耗余数、卸货向上结算和移除时限建议全部撤回。

### 8.1 分类

已确认采用“共享运输配置 + 自定义物品标签归属 + 默认运输配置”，不按注册名、模组名或组件猜测分类。

- 运输配置负责单位质量、运输词条，以及对应的显式货柜兼容类别；不提供市场价格或收购资格。
- 一个配置的归属标签可以列物品 ID，也可以引用 `#c:ingots` 等已确认标签。附魔、名称等组件参与载荷身份，不参与运输分类。
- 未匹配物品走默认运输配置；通用货柜显式接受默认类别，专用货柜仍按自己的白名单处理。默认质量及容量数值另定，不让所有货柜自动兼容一切。
- 命中多个不同配置时拒绝本轮新配置并列出冲突来源，不按文件顺序选、不叠加字段；修正标签清单后重载。
- 保留原 `CargoClass` 的贴花、兼容类别与分类容量能力，但清除旧商品路径推导；物品 ID 不再被要求写成 `类别/商品`。保留的是功能和美术，不是旧存档兼容。
- 当前柜内载荷使用装载时的运输快照。数据包重载只影响新装载；快照不一致时暂不允许追加，避免货物在途中变重或换词条。正常卸空后使用新规则。

### 8.2 固定数量损耗

用户明确现有词条扣的是实际完整度点数，百分比只是显示。因此新设计将扣完整度的动作替换为扣实际数量，而不是把损耗参数解释为百分比。

- 易碎示例：每次有效撞击扣 10 个，100 → 90 → 80；不是 100 → 90 → 81。扣量由词条决定，不是所有词条统一扣 10 个。
- 持续伤害改为每个有效周期扣固定整数个物品，间隔使用整数 tick；只保存必要的时间进度，不保存小数物品或损耗余数。
- 每次实际扣量为剩余数量与设定扣量中的较小值，归零后清除该载荷及其词条状态。
- 正常卸货、部分卸货、解包和追加均不因取整额外补扣物品。预览、失败请求、重复包不触发额外损耗。
- 触发检测仍可使用速度、温度等必要的物理数值，但扣量账本使用整数。现有小数 `damage_per_second` 等配置逐项重写为明确的整数扣量和间隔，不自动强转导致零伤害或过量伤害。
- 剩余物品保持原组件，质量随数量变化，交易只为实际转移的数量结算，不再乘完整度系数。

### 8.3 时限

**已确认保留并重构 `time_limit`：保护期结束后，每隔指定时间扣固定整数数量，直到卸空或损耗归零。** 到期不标整批失效，剩余货物仍可正常卸出和交易。

词条配置表达三个独立参数：保护期、到期后的扣量间隔、每次扣量。字段命名和数值在数据定义阶段落实，不在本次讨论中随意统一。

成功追加数量大于零且内容/运输快照兼容的货物时，可以刷新整个载荷的保护期，相当于补充冷却介质。无需判断追加比例，不额外发明介质物品消耗；原有已损失数量不会恢复。查看 GUI、重复请求、失败或数量为零的追加、保存重启不属于补货。

这是一段货柜运输的保护状态，不是物品终身保质期；普通物品不携带到期时间。冷冻物品或活物是词条用途说明，不扩大首版为实体运输兼容。

以下时间边界已确认，补算实现不得额外改变这些语义：

1. 使用服务端游戏 tick 而非现实时间，服务器停止时不推进；重启保存并恢复已有时间进度。
2. 保护期结束后再经过一个完整扣量间隔发生第一次扣量，而非在保护期结束瞬间扣一次。
3. 追加前先结算旧载荷已经到期应扣的周期，再提交实际追加并重置保护期和扣量时钟；不能通过刷新抹掉过去已经发生的损失。部分卸货不刷新保护期。
4. 时间词条在区块未加载时仍按游戏时间推进，重新加载或交互时先补算；环境、撞击等依赖实测条件的词条不能凭空推算离线环境。
5. 多个到期周期的补算采用有界整数计算，不逐周期循环，不超过实际剩余量，不让迟到的调度将伤害重复结算。

## 9. 第三批约定：转换设备与建点限制

用户已确认设备建议，并明确玩家贸易点全部终端/功能方块可放置在 Sable 上但不能绑定和使用，上限默认 1 且可配置。本轮不设建点冷却或创建费用。此文档仍描述重构目标，不代表业务代码已完成。

### 9.1 转换设备

- 首版分别提供物品打包、解包设备，一个核心允许绑定多台，均为可选设备，不新增必须终端指示灯或强制开业条件。
- 复用终端连接工具与 32 格绑定范围，绑定/解绑仍仅限核心所有者；操作和配置允许所有者及授权管理者，公共玩家不能手动操作。
- 设备需要核心、绑定和相应装卸区域有效，但不要求贸易点向公众营业；不能因暂停公共营业而停止工厂转换。
- 打包用装载区域、解包用卸载区域，各自只识别一个货柜，不支持切换。多个设备命中同一个货柜时，由服务端统一串行提交并校验载荷版本，不能分别缓存后覆盖彼此。
- 采用设备自身有界输入/输出缓冲对接物品自动化，转换直接发生在缓冲与货柜之间，不强制先经过仓库；转移多少只扣多少，堵塞保留余量。缓冲独立设限，不把全仓 5000 误用于所有货柜及机器。
- 纯转换不收货币、不生成交易经验，不调用公共终端的买卖结算；公共装卸交易仍正常扣款。若另增仓库直连口，后续明确设计，禁止绕过全仓 5000。
- 自动化访问缓冲的方式与手动管理权限分开：漏斗或管道不是玩家身份授权系统。设备有效绑定是自动加工前提；是否限制外部自动化方向可在模型/接口阶段确定，不承诺防止有物理访问权限的其他玩家通过外部管道投取物品。

### 9.2 建点与移动限制

- 按所有者 UUID、全存档跨维度统计玩家贸易点核心，未加载或暂停营业仍计数；管理授权不提供额外配额。上限默认 1，可在配置文件中修改，具体配置键和有效范围在数据接口阶段落实。
- 新建超额时拒绝创建有效核心，不自动解绑或删除其他贸易点。计数沿用现有核心索引，核心实际拆除后释放名额，允许在额度内立即重新建点；不添加迁移冷却记录。
- 首次建点与拆除后重建均不收取创建费用，不加入冷却等待。以后可能通过 VB 创建成本或其他机制约束频繁拆装，但仅记录为后续方向，本轮不添加相关扣款、占位配置或复杂防刷机制。
- **玩家贸易点所有终端和功能方块均允许正常放在 Sable 结构上，但不能绑定和使用**，包括核心、装卸终端、仓库管理、信息柜、航标、区域标记杆、打包/解包设备。不能以核心在世界而下属设备在结构中、或结构静止来绕过；不阻止放置/组装，不创建有效区域或执行贸易点业务。
- 对核心选定、连接器绑定和终端交互显示明确的“不支持在 Sable 物理结构上使用”提示；实际校验必须在服务端业务入口执行，不能只隐藏 GUI。自动处理也不得绕过设施所在结构的检查，不以每 tick 向玩家刷提示代替校验。
- 已绑定设施被带入结构时禁止继续工作，不因“不支持”自动删除方块、清空仓库或抹去绑定数据；后台索引、计数与返回静态世界后的恢复应与核心生命周期一致处理，避免幽灵节点或重复注册。
- 限制设施不等于禁止物理货柜：货柜仍可在 Sable 结构上运输，被静态玩家贸易点区域正常识别和装卸。普通贸易点、载具仪表等不因本规则一并禁用。
- 建点限额与位置限制不声称禁止背包运输、限制外围工厂，或抵挡多账号协作。是否允许长期在 NPC 附近建固定节点仍按原草案作为区位选择处理，不擅自新增 NPC 禁建圈。

### 9.3 本批确认结论

设备与建点主要规则已定案：可选多台转换设备，既有权限及区域内单货柜规则，设施在 Sable 上可放置但不能绑定和使用并提示，按所有者跨维度默认限 1 且可配置，本轮无拆除冷却、无创建费用。无需继续询问冷却时长；未来防频繁拆装和 VB 创建成本另行设计。
