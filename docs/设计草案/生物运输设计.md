# 生物运输设计

更新：2026-11-02。**生物打包机、黄色识别区域和按物种汇总的仓库视图已实现；捕获、柜内运输与释放尚未开放。** 本页维护待实现的活体运输规则；实施、参数确认和验收任务只在[待完成事项清单](待完成事项清单.md#生物专项)维护，不在此复制待办或历史方案。完成的运行契约再归入正式系统章节。

## 范围与分层

living 运输实际活体，不将刷怪蛋、鱼桶、蜂箱或普通生物材料当成实体载荷。液态和气态 Fluid 继续统一归 liquid；物品栏中的完整物品属于 solid。

活体运输分为实体准入、空间容量、逐只保存、环境与生命损耗四层。复用货柜唯一账本、装卸确认、占用锁、权限、环境观测、货柜能力、质量刷新和贸易结算生命周期；捕获、原生实体保存恢复及释放采用实际活体后端，不复用物品／流体的库存提取方式。

## 容量：舱位与单体尺寸

货柜总容量按整数“舱位”表达，不直接等于可装生物只数。还须声明单体最大宽／长／高、可支持的生活环境和最大实体数量。舱位是游戏空间预算，不等于真实立方米，不执行三维装箱或逐体素排列。

| 数据 | 规则 |
| --- | --- |
| 单只舱位占用 | 逐 EntityType 配置的正整数，可根据体型生成建议值，最终由数据包覆盖 |
| 总舱位使用量 | 所有存活个体冻结舱位之和，必须不大于柜体舱位容量 |
| 单体尺寸 | 每只必须符合柜体允许的运输包络；总舱位够用不代表超高、超长实体可以装入 |
| 幼体 | 首版按成年标准占用舱位，柜内暂停成长，不利用幼体缩小容量需求 |
| 特殊缩放 | 普通姿态或躺卧不减少占用；实际存在额外缩放的个体须核验真实尺寸，不能仅按注册类型默认值放行；特殊变体通过已验证的适配处理 |
| 实体数量上限 | 独立于舱位，限制大量微型实体的数据与操作成本；最终值待确定 |
| 数据大小上限 | 单体及整柜原生数据均有上限；超限拒绝捕获，不能截断后保存 |

首批识别配置及当前测试参数见[生物打包机](../11玩家贸易点/07_生物打包机.md#运输json)。正式舱位、质量平衡及BioPod／Aquarium各规格的运输尺寸、数量和数据大小上限仍须核定。

数量、舱位和质量分别计算。界面例如显示“8 mob，40 / 40舱位”；装卸旋钮1仍代表1只生物，报价与经验按实际交付的完整个体计，不出现半只生物。质量按单体配置及已支持携带内容计算，整柜载货质量最后向上取0.1Kpg，不用舱位、生命百分比代替质量。

## 实体准入

不按友好／中立／敌对统一禁止。普通敌对生物可以逐类开放，准入按明确支持、实体结构、当前状态、权限、尺寸和生活环境判断。

| 检查层 | 首版规则 |
| --- | --- |
| 基本对象 | 仅实际生物；玩家、掉落物、投射物、展示实体、载具等不作为活体货物 |
| 明确排除 | 末影龙、凋灵及明确禁止的特殊实体；首领不通过扩大柜体容量绕过限制 |
| 通用标签 | 拒绝 c:bosses、c:capturing_not_supported；c:teleporting_not_supported 作为禁止搬运依据，跨维度还须遵守原生实体限制 |
| 特殊结构 | 多部件实体、当前载客／骑乘、拴绳关联先拒绝，提示解除关系；不偷偷丢弃乘客或拴绳 |
| 当前状态 | 必须存活且未移除，不与传送、其他装卸或已登记运输事务冲突 |
| 配置与恢复 | 必须存在明确的运输支持定义，能够通过该类型保存恢复验证；仅写出NBT成功不能证明支持 |
| 权限 | 货柜及设施权限沿现有体系；驯服生物另核验原主人或明确授权，不因拥有装卸权即可搬走他人宠物 |
| 适配 | 每只均核验舱位、单体尺寸、生活环境及已验证的携带状态 |

通用标签不是完整名单，不能假设所有模组都已正确声明。项目依赖 NeoForge 21.1.233 已包含上述标签；定义见[NeoForge实体标签](https://github.com/neoforged/NeoForge/blob/1.21.1/src/main/java/net/neoforged/neoforge/common/Tags.java)。拒绝规则优先于普通允许配置；扩大支持不能绕过玩家、首领及无法安全恢复等边界。

## 逐实体类型属性与模组兼容

基础运输JSON已接入，现行路径、schema、质量、舱位、运输条件与贴花字段见[生物打包机](../11玩家贸易点/07_生物打包机.md#运输json)。后续捕获还需明确标准运输尺寸、生活环境、携带内容与恢复验证；价格和交付经验继续放在贸易点报价中。

缺失定义默认不支持捕获，提示“该生物尚未配置运输支持”。不对未知模组实体套用一个默认质量后自动开放。标准保存机制、无特殊外部关联的模组生物，可验证后用数据包开放；特殊行为才增加实际适配，不为未知模组预建空接口。

原生生物有可持久化的附加数据，也有纯运行时数据。保存应走实体原生持久化流程并保留可恢复的模组数据，不手工只挑名称、生命等少数字段，也不承诺所有外部系统关联均能由NBT恢复。[NeoForge附加数据说明](https://docs.neoforged.net/docs/1.21.1/datastorage/attachments/)

后续仅扩展捕获与恢复实际需要的属性，不重复建立基础属性协议；尺寸、生活环境和特殊适配字段尚待定稿。

## 柜内逐只记录与批量身份

首版一柜只装同一 EntityType、同一套冻结运输规则的个体，不开放混种。名称、年龄、UUID等个体差异不要求完全一致，否则无法组成正常批量；规则或适配不相容的变体须分柜。

| 层次 | 保存内容 |
| --- | --- |
| 批量分类 | EntityType、运输规则／环境与适配档案，不用每只UUID作为商品分类 |
| 个体记录 | 原UUID、完整持久化实体数据、当前生命、必要显示摘要、冻结舱位与质量 |
| 运输会话 | 共用环境状态、条件暴露进度、已结算时间及事务状态，不为每只生物重复采样环境 |

名称、当前生命、最大生命相关属性、年龄、变种、驯服关系和已经支持的装备状态应保留。实体不在柜内实际生成，不运行AI、寻路、繁殖、成长、原生饥饿、自然回血或效果计时；只推进已声明的运输环境和运输扣血。柜内不是全生态模拟。

释放时重新设置目的地位置、速度等运行状态，不照搬原位置。巢穴、工作点、睡床等世界关联需要专项验证；村民、蜜蜂等复杂关联生物不随普通动物自动开放。非空背包、箱载货物等首版限制；装备、鞍等支持范围逐首批实体验证，不能静默删除未知携带内容后放行。

## 捕获、释放与唯一性

保留原UUID，维护世界实体与柜内记录的唯一归属；不存在因冲突换UUID继续生成的兜底。柜内数据与世界实体跨存储文件，不把普通内存操作顺序当成崩溃原子性，需有持久化事务状态与恢复核验。

1. 确认界面只预览候选实体、空间、质量和费用，不提前移除实体。
2. 提交时重新核验原实体、所有权、存活状态、尺寸、完整数据和剩余容量，并阻止其他事务重复占用。
3. 捕获与释放使用明确的归属转移过程；普通失败补偿，崩溃／重启按事务记录核验，不生成第二份。
4. 释放逐只查找已加载范围内的有效位置，验证净空、碰撞、生活环境及加入世界的实际结果。只提交成功转移的个体，未成功部分保留在柜内；预览和最终结算按实际成功数量重验。
5. 原UUID冲突、目标未加载、被其他模组拒绝加入或数据缺失时停止相应操作并保留记录。不能覆盖世界实体、强制加载、换UUID或把损坏载荷当空柜。
6. 缺失模组／实体类型或损坏数据保留可诊断原文并隔离，不删除成空柜，也不把尚未恢复的个体当作已死亡。

识别入口已由生物打包机提供；捕获提交、释放位置、跨维度开放范围和事务恢复仍待实现。沿用现有确认、取消与强制终止权限，不承诺仅靠现有物品回滚即可保证活体唯一性。

## 运输货损：所有存活个体统一扣生命

**已确认：生物货损扣生命值，不直接扣“生物数量”；一次有效运输伤害对柜内所有存活个体分别施加相同数值。**

设本次按运输条件与货柜能力结算的伤害为D，对每只生物i执行：

> 新生命值_i＝max(0，旧生命值_i－D)

D使用原生生命值单位，2点通常对应1颗心；不是最大生命百分比，不是先算整柜伤害再按只数分摊，也不因柜内有N只就对每只额外乘N。生命值可保留合法小数，不套用货币整数或质量一位小数的向上取整。

例如柜内三只生物生命分别为20、10、3，一次有效伤害4后分别为16、6、0；前两只原样保留，第三只死亡移除。生物耐受差异由其实际生命及声明运输规则体现；数量只随真实死亡或交付而改变。

不同条件的伤害沿共用条件求值规则结算，不能将同一次暴露或冲击重复处理。运输扣血是保存记录的生命变化，不调用世界实体的战斗伤害、无敌帧或完整死亡流程；装备的战斗减伤不自动参与，运输保护由柜体能力决定。实际每次／每周期伤害、阈值与宽限仍需逐实体类型配置，不把物品的“每次扣10pcs”直接解释为“死亡10只”。

### 死亡与载荷更新

- 生命归零即从可运输的存活记录中移除，对应死亡归属一次性终结；不会因重启、重试、取消或释放恢复成活体。
- **不产生任何掉落物。** 生物本体战利品、装备、已支持携带内容均不返还；也不生成尸体物品或经验球，不触发原生击杀产物流程。
- 不为触发掉落而临时生成／杀死世界实体。批量死亡只更新账本、必要事务状态和显示摘要。
- 死亡后同步减少存活数量、舱位占用和该个体质量；受伤但仍存活不按生命比例减轻质量或舱位。
- 所有个体死亡时清空有效活体载荷，柜体仍保留；不会支付交付货款或产生交付经验。
- 追加、部分卸载、数据重载和重新打开界面不回血、不重置已有暴露／伤害进度。取消装卸不撤回已经实际结算的运输伤害。

### 性能边界

环境采样和运输条件求值按同一冻结规则组执行；只有发生有效伤害时才有界处理相应个体生命记录，不逐Tick生成实体或反复序列化全部NBT。保存保留必要原文与生命更新，客户端只接收数量、舱位、质量、生命摘要和状态，不广播全柜实体NBT。最大数量／字节上限用于约束捕获、释放及伤害批处理成本；具体预算以实测确定。

## 通用设施与交互

已实现的识别区域、物流接口、物种库存和刷新规则统一维护在[生物打包机](../11玩家贸易点/07_生物打包机.md)，本页只约定后续装卸行为。

### 后续装卸规则

复用通用装卸终端、实体按钮、装卸确认GUI和PDA详情入口，不新建专用生物装卸终端或专用GUI。普通装载终端和仓库管理终端均按物种选择，由服务端在确认时依据后续核定的自动选择规则选择实际个体；本轮识别视图不构成捕获授权。

货柜同一时间只运输一种物种。每只保存完整原生持久化数据，卸载严格按装载顺序的反序执行：装入1、2、3、4，则先卸4，再3、2、1。若栈顶个体无法安全释放就停止本次操作，不跳过它选择更早个体。只按实际成功移交的只数、舱位和质量结算。

通用确认界面显示物种图标和名称、只数、舱位、质量及费用；缺少数据使用“---”。货柜详情不提供逐只列表，只显示当前生命最低个体的当前／最大生命，不能用平均生命掩盖濒死个体。羊的毛色等差异由各自记录在卸载时恢复，物种图标使用统一预览。

权限、重复请求、取消和强制关闭沿用通用会话边界，但原生捕获释放仍需单独实现唯一归属与恢复事务。不能因为共用GUI就假定已具备实体转移原子性。驯服、装备、拴绳等准入与授权细节在待办中继续核定。


## 共用生命周期与仪表调整边界

先从现有具体装卸终端判断中提取共用操作上下文，使通用终端的生物业务可以复用会话、权限、货柜占用、防重放、取消与提交重验；原生捕获释放与崩溃恢复仍采用专用后端。共用数据摘要与生物个体／舱位快照分层，不持续给现有单货物数据包追加大量无关字段。

现有装卸终端的仪表布局、显示字段、按钮和确认界面统一调整；生物沿用通用布局并补充类型化摘要，不新增独立终端或专用GUI。界面具体排布、模型表面位置、素材及按钮编号尚待用户定稿，不在草案中虚构坐标。详细边界见[装卸终端显示与交互调整](装卸终端显示与交互调整.md)，实施和验收只在统一待办维护。

## 捕获运输验证边界

在现有鸡、牛、羊、猪、僵尸识别配置上验证小／大体型及敌对生物捕获，正式投放清单与平衡参数仍待核定。先跑通单体捕获、保存、重启与原样释放，再验证同类批量、共同舱位和统一扣血；随后扩展水生、驯服及模组实体。

验收必须覆盖三只不同当前生命在相同伤害下各自扣血、部分死亡与全部死亡、无掉落／装备返还／经验球、死亡不重生、数量舱位质量同步、重复采样不重复伤害，以及物种汇总、自动选择重验、后进先出卸载、围栏失效、通用确认与最低生命显示、捕获／释放取消、失败、重启和UUID冲突。完整任务只维护于[生物专项](待完成事项清单.md#生物专项)。
