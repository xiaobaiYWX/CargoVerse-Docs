# 贸易点结构制作指南

本文说明如何把贸易点制作成可生成、可绑定、可测试的世界结构。经济规则见[贸易点运行时与经济](01_贸易点运行时与经济.md)。

## 1. 最小生成链路

```text
structure_set
  -> worldgen/structure
  -> start template_pool
  -> structure/*.nbt 与子级 template_pool
  -> trade_point_structure_bindings
  -> 运行时为结构内方块实体注入同一个 tradePointId
```

## 2. 最小文件集

以 `cloud_farm` 为例：

```text
data/cargoverse/
├─ structure/trade_point/resource/cloud_farm/
│  └─ fixed_buildings/farmhouse.nbt
├─ worldgen/template_pool/trade_point/resource/cloud_farm/
│  └─ start.json
├─ worldgen/structure/cloud_farm.json
├─ worldgen/structure_set/cloud_farm.json
├─ tags/worldgen/biome/has_structure/cloud_farm.json
└─ trade_point_structure_bindings/resource/general/cloud_farm.json
```

NBT 文件路径就是结构资源 ID，去掉 `structure/` 和 `.nbt` 即可：

```text
structure/trade_point/resource/cloud_farm/fixed_buildings/farmhouse.nbt
-> cargoverse:trade_point/resource/cloud_farm/fixed_buildings/farmhouse
```

## 3. 结构清单

至少先确定：

- 世界结构 ID 与贸易点定义 ID；
- 起始模板、固定模块和可选模块；
- 模块之间的有向连接关系；
- 贸易点信息柜、业务终端和三类定位点的位置；
- 维度、群系、高度与生成间距；

这些内容应写入具体贸易点文档，不在通用规范中重复描述其经济定位。

## 4. 制作 NBT 模板

### 4.1 拆分原则

一个模板对应一个能独立保存和拼接的模块，例如主楼、平台、道路或农田。

### 4.2 保存要求

- 结构边界尽量贴合实际方块；保存范围内的空气也会参与碰撞判定。
- Jigsaw 方块放在模块边缘，子模块应从父模块边界外开始。
- 不要把测试方块、临时标记或固定 UUID 保存进模板。
- 建筑、平台、终端区域通常使用 `rigid`。
- 道路、农田等需要贴合地形的模块可使用 `terrain_matching`。
- Processor 只用于材质替换或轻量变化，不负责改变整体几何形状。

### 4.3 贸易点方块实体

目前结构绑定会处理以下方块实体／接口：

- `TradePointRegistrationAnchor`（当前由贸易点信息柜承担主注册锚点）；
- `CargoManufacturingPlatformBlockEntity`、`LicenseRegistrationTerminalBlockEntity`、`ShipIdentifierBlockEntity`、`ItemVendingMachineBlockEntity`；
- `ProductionLineTerminalBlockEntity`、`WarehouseInformationCabinetBlockEntity`；
- `ContainerLoaderBlockEntity`、`CargoUnloaderBlockEntity`；
- `CargoLocatorBlockEntity`。

装饰性的 `trade_point_terminal` 没有方块实体，不参与绑定注入，也不能成为主注册锚点。

模板中只放置并配置业务所需字段。结构生成后，运行时会向同一结构内的相关方块实体注入相同且稳定的 `tradePointId`。

## 5. Jigsaw 最小规则

连接的核心关系只有一条：

```text
父接口 target = 子接口 name
```

父接口示例：

```text
pool        = cargoverse:trade_point/resource/cloud_farm/roads
name        = cargoverse:cloud_farm/start/to_road_a
target      = cargoverse:cloud_farm/road_a/input
final_state = minecraft:air
```

子接口示例：

```text
pool        = minecraft:empty
name        = cargoverse:cloud_farm/road_a/input
target      = minecraft:empty
final_state = minecraft:air
```

制作时遵守以下约束：

- 两个接口必须相向放置。
- 固定连接的 `target/name` 应唯一，避免接到错误模块。
- 被动接入口使用 `minecraft:empty`，防止反向继续生成。
- 不要设计循环、自引用或要求两条分支最终同时合并的拓扑。
- 需要视觉闭环时，只保留一条实际生成链，另一端用建筑外观闭合。
- 不同占地尺寸的候选模块应拆分到不同模板池。

推荐把结构理解为一棵树：起始模块是根，固定建筑、道路和装饰是逐层展开的子节点。

## 6. 建立模板池

起始池示例：

```json
{
  "fallback": "minecraft:empty",
  "elements": [
    {
      "weight": 1,
      "element": {
        "element_type": "minecraft:single_pool_element",
        "location": "cargoverse:trade_point/resource/cloud_farm/fixed_buildings/farmhouse",
        "processors": "minecraft:empty",
        "projection": "rigid"
      }
    }
  ]
}
```

固定池可以包含多个模板，但每个固定插槽应使用唯一的接口名。随机插槽则让多个候选模板共用同一个接入口名，通过 `weight` 控制权重；允许留空时加入：

```json
{
  "weight": 1,
  "element": {
    "element_type": "minecraft:empty_pool_element"
  }
}
```

## 7. 建立世界生成文件

### 7.1 Worldgen Structure

`data/cargoverse/worldgen/structure/cloud_farm.json`

```json
{
  "type": "minecraft:jigsaw",
  "biomes": "#cargoverse:has_structure/cloud_farm",
  "step": "surface_structures",
  "spawn_overrides": {},
  "terrain_adaptation": "beard_thin",
  "start_pool": "cargoverse:trade_point/resource/cloud_farm/start",
  "size": 6,
  "start_height": { "absolute": 0 },
  "project_start_to_heightmap": "WORLD_SURFACE_WG",
  "max_distance_from_center": 116,
  "use_expansion_hack": false
}
```

`size` 是最大拼接深度，不是建筑数量。先使用能覆盖当前连接树的最小值，再按测试结果调整。

### 7.2 Structure Set

`data/cargoverse/worldgen/structure_set/cloud_farm.json`

```json
{
  "structures": [
    { "structure": "cargoverse:cloud_farm", "weight": 1 }
  ],
  "placement": {
    "type": "minecraft:random_spread",
    "salt": 15487029,
    "spacing": 32,
    "separation": 12
  }
}
```

必须满足 `spacing > separation`。正式值应结合贸易点稀有度和实机探索距离统一调整。

### 7.3 群系标签

`data/cargoverse/tags/worldgen/biome/has_structure/cloud_farm.json`

```json
{
  "replace": false,
  "values": ["#minecraft:is_overworld"]
}
```

首轮测试可放宽群系范围；确认结构正常后再收窄到目标群系。

## 8. 绑定贸易点定义

结构绑定目录必须先按贸易点类型分成 `factory`、`market`、`resource` 三类，随后可以继续按内容类别建立子目录：

```text
data/<namespace>/trade_point_structure_bindings/
├─ factory/<category>/<name>.json
├─ market/<category>/<name>.json
└─ resource/<category>/<name>.json
```

内置云天农庄绑定位于：

`data/cargoverse/trade_point_structure_bindings/resource/general/cloud_farm.json`

完整格式如下，三个根字段和候选项的两个字段都不可省略：

```json
{
  "schema_version": 1,
  "structure": "cargoverse:cloud_farm",
  "trade_point_definitions": [
    {
      "weight": 1,
      "definition": "cargoverse:resource/general/default"
    }
  ]
}
```

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `schema_version` | 是 | 当前只能为整数 `1` |
| `structure` | 是 | 完整的 `worldgen/structure` ID；不是模板池或 `structure_set` ID |
| `trade_point_definitions` | 是 | 1～256 个加权候选，不允许空数组 |
| `trade_point_definitions[].weight` | 是 | 整数 `1～1000000`；`0` 不能用于禁用候选 |
| `trade_point_definitions[].definition` | 是 | 已加载的完整贸易点定义 ID |

绑定文件只接受这些字段，不接受旧字段 `structures_pool`、`trade_point_id`、候选项 `id`，也不接受额外未知字段。绑定目录大类必须和每个候选贸易点定义 ID 的第一段一致，例如 `resource/general/cloud_farm.json` 只能引用 `namespace:resource/...` 定义。

同一世界结构只能由一个绑定文件负责。缺少字段、目录类别错误、空候选池、重复候选、非法权重、悬空贸易点定义、跨类别引用或多个文件绑定同一个世界结构，都会拒绝整次数据包重载；不再静默回退默认贸易点。

### 8.1 自然生成与手工搭建的统一注册

- 自然生成：结构绑定文件抽取贸易点定义，贸易点信息柜作为注册锚点保存定义与实例 UUID；结构内其他终端只获得 UUID。
- 手工搭建：贸易点信息柜自动生成 UUID；管理员在它的 GUI 中填写贸易点定义 ID，再把该 UUID 填入其他终端。
- 只有贸易点信息柜可以写入“UUID → 定义”注册。装载机、卸载机、仓库信息柜、生产线终端、商店等只接受 UUID，不得增加贸易点定义路径输入框或本地定义回退。
- GUI 中填写的是 `namespace:type/category/name` 形式的定义 ID，不是 `data/...json` 文件系统路径。未加载、格式非法或悬空的 ID 由服务端拒绝。
- 同一 UUID 应只保留一个有效信息柜锚点；复制信息柜时应为新站点生成新 UUID，功能终端才共享目标站点 UUID。

代码层将两种职责拆成独立契约：贸易点信息柜实现注册锚点，接收“UUID + 定义 ID”；普通功能终端实现 `TradePointInstanceBindingTarget`，只接收 UUID。结构生成桥只依赖这两个契约，不再枚举装载机、卸载机、商店等具体方块实体类型。新增贸易点功能终端时，实现 UUID 绑定契约即可纳入自然生成绑定，不应向结构生成桥追加具体类型分支。

## 9. 推荐制作顺序

1. 填写贸易点结构设计单。
2. 只制作起始模板和最少固定模块。
3. 建立模板池、世界结构、结构集和群系标签。
4. 使用 `/place structure` 验证拼接与朝向。
5. 添加贸易点绑定，检查终端获得的 `tradePointId`。
6. 在新区域验证自然生成与 `/locate structure`。
7. 最后添加随机建筑、装饰、材质变化和稀有度调优。

## 10. 发布前检查

### NBT 与拼接

- [ ] 所有模板均能被结构方块正常加载。
- [ ] 起始模板可以单独生成。
- [ ] 父 `target` 与子 `name` 完全一致。
- [ ] 接口相向，模块不重叠且没有明显空隙。
- [ ] 没有循环、自引用和意外反向生成。
- [ ] 模板边界没有多余空气导致碰撞。

### 数据文件

- [ ] 所有资源 ID 与实际路径一致。
- [ ] 模板池的 `location` 均存在。
- [ ] 世界结构引用正确的起始池和群系标签。
- [ ] `spacing > separation`，且 `salt` 已确定。
- [ ] 绑定文件引用的是世界结构 ID 和有效贸易点定义 ID。

### 游戏内测试

- [ ] `/reload` 无报错。
- [ ] `/place structure cargoverse:<结构ID>` 成功。
- [ ] `/locate structure cargoverse:<结构ID>` 可定位。
- [ ] 新区块可自然生成；旧区块不会因数据更新自动重建。
- [ ] 同一贸易点内相关方块实体获得相同 `tradePointId`。
- [ ] 功能终端只保存 UUID；只有信息柜保存并编辑贸易点定义 ID。
- [ ] 手工搭建的信息柜绑定有效定义后，同 UUID 的终端可以解析并使用该贸易点。
- [ ] 重新进入世界后 ID 与终端功能仍正常。

## 11. 故障速查

| 现象 | 优先检查 |
|---|---|
| 完全不生成 | worldgen structure、structure set、群系标签和资源 ID |
| 只生成起始模块 | 起始模块 Jigsaw 的 pool、target 和结构 `size` |
| 接到错误建筑 | 接口名不唯一，或随机候选错误共用入口名 |
| 模块重叠 | 模板保存边界、接口朝向和连接点位置 |
| 拼接中途停止 | 子 `name` 不匹配、模板池为空或达到深度限制 |
| 终端没有贸易点 ID | 绑定文件分类路径、`structure`、`trade_point_definitions` 和方块实体类型 |
| 修改后看不到变化 | 旧结构不会重建，应在新位置重新 `/place` 或测试新区块 |
