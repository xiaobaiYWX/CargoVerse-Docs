# 货柜制造台定义

> 已实现：定义解析、严格字段校验、货柜／货币悬空引用校验、贸易点模块引用校验、原子重载发布、按贸易点既有输入库存类型筛选配方、库存材料候选的稳定排序、`stock_costs` 的原子库存扣减与失败补偿，以及制造台按贸易点抽中的配方完成货币、材料和货柜生成事务。

货柜制造台定义位于：

```text
data/<namespace>/trade_points/trade_points_subfunctions/
  cargo_manufacturing_platform_definitions/<path>.json
```

文件相对上述目录的路径就是定义 ID。例如：

```text
data/cargoverse/trade_points/trade_points_subfunctions/
  cargo_manufacturing_platform_definitions/resource/general/default.json
```

对应 `cargoverse:resource/general/default`，由贸易点的 `modules.cargo_manufacturing_platform.definitions_pool[].definition` 引用。

## 完整示例

```json
{
  "schema_version": 1,
  "display_name": "基础货柜制造台",
  "recipes": [
    {
      "id": "cargo_box_s_basic",
      "min_prosperity_level": 1,
      "required_license_level": "S",
      "cargo_container_definition": "cargoverse:aui/atlas_sd_l",
      "currency_cost": {
        "currency": "cargoverse:enderite",
        "amount": 80
      },
      "stock_costs": [
        {
          "match_mode": "any",
          "tags": ["stone"],
          "amount": 8.0
        },
        {
          "match_mode": "any",
          "tags": ["ore"],
          "amount": 10.0
        }
      ]
    }
  ]
}
```

`cargo_container_definition` 使用货柜定义自身的资源 ID，即相对 `data/<namespace>/cargo_containers/` 的路径。不要把目录名再写进 ID；`cargo_containers/aui/atlas_sd_l.json` 的 ID 是 `cargoverse:aui/atlas_sd_l`，不是 `cargoverse:cargo_containers/aui/atlas_sd_l`。

## 顶层字段

| 字段 | 必填 | 格式与范围 | 作用 |
| --- | --- | --- | --- |
| `schema_version` | 是 | 整数，当前只能为 `1` | 定义结构版本 |
| `display_name` | 是 | 非空字符串或非空 Minecraft Component JSON | GUI 与调试信息中的制造台名称 |
| `recipes` | 是 | `1..256` 个对象 | 当前定义提供的制造选项 |

顶层、配方、货币成本和库存成本对象都采用严格字段集合；出现拼错或未知字段会拒绝整轮数据重载。

## `recipes[]`

| 字段 | 必填 | 格式与范围 | 作用 |
| --- | --- | --- | --- |
| `id` | 是 | `[a-z0-9_.-]+`，同一文件内唯一 | GUI、网络消息、日志及未来运行时保存使用的局部配方 ID |
| `min_prosperity_level` | 是 | 非负整数 | 贸易点低于此繁荣等级时不可制造 |
| `required_license_level` | 是 | `S`、`M`、`L`、`X`、`XL` 或 `SP` | 玩家最低货运许可等级 |
| `cargo_container_definition` | 是 | 有效资源 ID | 制造结果引用的现有货柜定义；不内联容量、模型或物理数据 |
| `currency_cost` | 是 | 对象 | 玩家承担的货币成本 |
| `stock_costs` | 是 | `0..64` 个对象 | 从当前贸易点既有 `input_stock` 行承担的材料成本 |

第一版要求始终保留 `currency_cost`；免费配方写 `amount: 0`。`stock_costs` 可以为空，表示该配方不消耗贸易点库存材料。

## `currency_cost`

| 字段 | 必填 | 格式与范围 | 作用 |
| --- | --- | --- | --- |
| `currency` | 是 | 已存在的货币组资源 ID | 从玩家账户或持有货币扣除的币种 |
| `amount` | 是 | 有限数字，`0..1000000000000` | 玩家货币成本，允许整数或小数 |

该成本属于玩家资源，不是贸易点库存，也是货柜制造价格的唯一权威来源。货柜定义不再接受 `base_value`，制造商也不再提供 `value_multiplier`。当前整数货币结算会把 `amount` 四舍五入并限制在整数范围内；生成失败时沿用可退款支付回执。

## `stock_costs[]`

| 字段 | 必填 | 格式与范围 | 作用 |
| --- | --- | --- | --- |
| `match_mode` | 是 | `any` 或 `all` | 标签匹配方式 |
| `tags` | 是 | 至少一个 `[a-z0-9_.-]+` 标签 | 在已有输入库存中筛选 CargoGood |
| `amount` | 是 | 有限数字，`>0` 且不超过 `1000000000` | 需要消耗的 CargoGood 单位数量，当前通常为 t |

- `any`：CargoGood 拥有 `tags` 中至少一个标签即可匹配；
- `all`：同一个 CargoGood 必须同时拥有 `tags` 中全部标签；不是从多个货物拼出标签集合。

## 库存匹配边界

制造条目首先按当前贸易点的 `input_stock` 类型集合进行可见性筛选，并用这些类型对应的 CargoGood 定义中的 `tags` 判断。若任意一项 `stock_costs` 找不到真实匹配类型，整条配方不会进入制造台的制造条目列表。

类型存在与库存足够是两个不同条件：`input_stock` 中已有匹配 CargoGood 行，即使其当前数量为 `0`，该制造条目仍然显示；数量不足只会让对应材料状态显示为不可用。实际材料候选和可用数量只统计数量为正的匹配行。

边界规则如下：

- 不扫描全局 CargoGood 表来创建新库存；
- 不向贸易点收购列表或生产线增加货物；
- 不创建抽象“标签库存”；
- 不把 `tags` 拼成临时货物名称，也不为缺失的匹配结果生成虚拟 CargoGood 行；
- 未知 CargoGood 不构成类型匹配；数量为 `0`、负数或非有限数的库存行不贡献可用数量；
- 没有满足某项成本的既有输入类型时，该配方不显示；有匹配类型但数量不足时，配方显示但不可制造。

多个已有库存同时满足同一成本时，候选顺序固定为：

1. `tech_level` 较低；
2. `base_value` 较低；
3. 当前库存数量较多；
4. CargoGood 完整 ID 字典序。

实际扣料允许同一项成本跨多个候选 CargoGood 补足。例如需要 `10t ore` 时，可以依次扣除 `8t iron_ore` 与 `2t copper_ore`。同一配方的 `stock_costs` 按 JSON 数组顺序处理，并共享一份逐步减少的临时库存，因此标签范围重叠的多个成本项不会重复消费同一批库存。任一项无法补足时，整条配方不可制造，且不会发生部分扣料。

## 制造事务

玩家按下制造按钮后，服务端在同一串行事务中重新读取实时配方、许可等级、调度点、玩家货币和贸易点库存，不信任客户端此前看到的快照。流程为：

1. 按上述稳定顺序为整条配方生成完整材料扣除计划；
2. 扣除玩家 `currency_cost`；
3. 按计划原子扣除贸易点 `input_stock`；
4. 在终端配置的生成位置放置并注册货柜；
5. 写入贸易点设备交易统计并提交事务。

货币扣除和库存扣除都持有同步回执。材料不足、生成区域被占用、模板放置失败或提交前发生异常时，会按逆序移除本次已生成的货柜、恢复贸易点库存并退回玩家货币。多个玩家同时使用制造台时由服务端串行执行，后到请求会基于前一个请求提交后的库存重新规划，不能超卖或重复扣料。

## 当前实现分层

货柜制造台链路按职责拆分，避免方块实体、显示代码和交易代码各自解释一遍库存：

1. `CargoManufacturingPlatformDefinition` 与其重载器负责 JSON 结构、范围和悬空引用校验；
2. `CargoManufacturingOfferService` 一次解析贸易点模块绑定、制造台定义、繁荣度和实时输入库存，并发布同一时点的 `Catalog`；
3. `CargoManufacturingStockSnapshot` 是持久化字符串库存与运行时 `ResourceLocation` 库存之间唯一的制造链路转换层；
4. `CargoManufacturingMaterialMatcher` 只负责可见性、候选排序、充足性判断和确定性扣料计划，不修改世界状态；
5. `CargoManufacturingDisplayService` 把目录与材料评估投影成仪表快照，方块实体只保存选择位置和同步结果；
6. `CargoManufacturingPurchaseService` 作为大型制造台的稳定入口，实际服务端校验和补偿事务集中在 `CargoManufacturingTransaction`；
7. `TradePointInventoryService` 执行原子输入库存扣除并提供精确回滚回执。

大型制造台刷新世界表面仪表时，会先取得一份制造目录再派生价格、许可、预览和货柜快照，不重复恢复同一个贸易点状态。客户端显示快照只用于展示，制造按钮始终触发服务端重新规划。

## 重载与引用

货柜制造台定义与货物、厂商、货柜、货币组、生产线池、商店定义、贸易点定义和结构绑定在同一轮 `CargoDataReloadListener` 准备阶段交叉校验。下列情况都会保留旧快照并拒绝发布新数据：

- JSON 不是对象、字段缺失、未知字段或数值越界；
- 配方 ID 重复、许可等级或匹配模式未知；
- 引用的货柜定义或货币组不存在；
- 贸易点 `cargo_manufacturing_platform` 模块引用的制造台定义不存在。

同 ID 仍按数据包优先级整项覆盖，不合并 `recipes` 数组。贸易点实例注册时抽中的定义 ID会持久化；重载不会自动重抽。

实现依据：`manufacturing/CargoManufacturingPlatformDefinition.java`、`manufacturing/CargoManufacturingPlatformDefinitionReloadListener.java`、`manufacturing/CargoManufacturingOfferService.java`、`manufacturing/CargoManufacturingStockSnapshot.java`、`manufacturing/CargoManufacturingMaterialMatcher.java`、`manufacturing/CargoManufacturingDisplayService.java`、`trade/CargoManufacturingTransaction.java`、`trade/TradePointInventoryService.java`、`cargo/data/CargoDataReloadListener.java`。

制造台展示货柜可装载范围时读取目标货柜定义的 `allowed_cargo_classes`，并在 Cargo Class 缩微胶卷仪表中直接绘制分类贴花。这里不枚举或显示 CargoGood 图标；具体货物只在库存材料行中按 CargoGood 显示。
