# 物品售货机与商店定义

> 已实现：严格商店定义、注册时稳定抽取、世界表面商品列表与按钮、库存推导、服务器权威购买、共享待领取区、拆除掉落和补偿事务。仍需执行真实双客户端竞争、断线和高延迟实机矩阵。

## 职责边界

物品售货机出售普通物品。它不直接持有商店定义路径，而是只绑定贸易点 UUID，再读取该贸易点注册记录中的 `modules.item_shop` 抽取结果。

- 贸易点注册时即抽取并持久化商店定义与上架商品，是否实际放置售货机不影响抽取。
- 手动放置的售货机初始 UUID 为空，仪表保留但显示未绑定／空内容。
- 售货机管理员 GUI 只填写贸易点 UUID，不接受定义文件路径。
- 同一贸易点 UUID 下的售货机共享贸易点输出库存，但各自持有独立待领取区。
- 旧商店终端、购物车 Screen／Menu 和旧定义格式不再兼容。

货币字段只能引用已加载的货币组，实体支付和多面额找零见[实体货币与多面额结算](../07货币系统/01_实体货币与多面额结算.md)。

## 文件位置与定义 ID

```text
data/<namespace>/trade_points/trade_points_subfunctions/shop_definitions/<path>.json
```

定义 ID 是 `shop_definitions/` 后的相对路径。例如：

```text
data/cargoverse/trade_points/trade_points_subfunctions/shop_definitions/resource/general/default_shop.json
→ cargoverse:resource/general/default_shop
```

## 完整数据结构

```json
{
  "schema_version": 1,
  "display_name": "默认资源商店",
  "catalog": {
    "draw_count": 5,
    "allow_duplicates": false
  },
  "offers": [
    {
      "id": "iron_ingot_pack",
      "weight": 1,
      "unlock_prosperity_level": 0,
      "result": {
        "type": "item",
        "item": "minecraft:iron_ingot",
        "count": 3
      },
      "price": {
        "currency": "cargoverse:enderite",
        "amount": 64
      },
      "output_costs": [
        {
          "match_mode": "any",
          "tags": ["ore", "metal"],
          "amount": 1.0
        }
      ]
    }
  ]
}
```

顶层、`catalog`、`offers[]` 及其子对象均采用严格字段集合；缺字段、未知字段、重复 offer ID、未知物品／货币、非法标签或越界数值都会使整轮数据发布失败。

### 顶层与抽取字段

| 字段 | 作用 |
| --- | --- |
| `schema_version` | 当前固定为 `1`。 |
| `display_name` | 商店定义显示名，支持项目统一文本结构。 |
| `catalog.draw_count` | 贸易点注册时抽取的商品次数，范围 `0..256`。 |
| `catalog.allow_duplicates` | 是否允许同一 offer 被重复抽中。 |
| `offers` | 候选商品数组，必须包含 `1..256` 项。 |

### `offers[]`

| 字段 | 作用 |
| --- | --- |
| `id` | 定义内唯一稳定 ID，只允许小写字母、数字、`_`、`.`、`-`。用于注册持久化与运行时查找。 |
| `weight` | 大于 `0` 才参与加权抽取；数值越大，抽中概率越高。 |
| `unlock_prosperity_level` | 商品显示与购买所需的最低贸易点繁荣等级。 |
| `result.type` | 第一版只支持 `item`。 |
| `result.item` | 购买后暂存的已注册物品 ID。 |
| `result.count` | 每份购买生成的物品数，最小为 `1`。 |
| `price.currency` | 已加载货币组 ID。 |
| `price.amount` | 每份购买的支付价值，可为 `0`。 |
| `output_costs` | 每份购买消耗的贸易点产出库存条件，最多 64 项；空数组表示不消耗 CargoGood。 |

## `output_costs[]` 与标签匹配

```json
{
  "match_mode": "any",
  "tags": ["stone", "clay", "sand"],
  "amount": 8.0
}
```

| 字段 | 作用 |
| --- | --- |
| `match_mode` | `any`：CargoGood 具有任意一个标签即可；`all`：必须同时具有全部标签。 |
| `tags` | 非空 CargoGood 标签集合，不是库存 ID。 |
| `amount` | 每份购买需要消耗的数量，使用 CargoGood 库存单位，当前通常为 `t`。 |

必须遵守以下原则：

1. 只遍历贸易点生产布局中已经存在的 `output_stock` 行。
2. 不从全局 CargoGood 表凭空生成库存，不添加输出行，不修改生产／出售列表。
3. 注册抽取时，某 offer 的每项成本都必须至少能匹配该贸易点的一种输出 CargoGood，否则该 offer 不进入候选池。
4. 运行时库存数量不足时，offer 仍可显示，但余量为 `0` 或实际可购买次数，购买被拒绝。

当多个现有 CargoGood 同时符合一个成本条件时，统一按以下顺序消耗：

1. `tech_level` 较低；
2. `base_value` 较低；
3. 当前库存较多；
4. CargoGood ID 字典序。

例如每份铁锭消耗 `1t`、当前可匹配的 output stock 合计为 `12t`，库存余量仪表显示 `12`。购买数量调整为 `3` 后，服务端会再次计算并原子消耗 `3t`。

## 贸易点模块绑定

```json
"modules": {
  "item_shop": {
    "min_prosperity_level": 1,
    "definitions_pool": [
      {
        "weight": 1,
        "definition": "cargoverse:resource/general/default_shop"
      }
    ]
  }
}
```

贸易点注册时先从 `definitions_pool` 加权抽取定义，再根据贸易点已固定的输出 CargoGood 集合抽取 offer，并把稳定 offer ID 一并保存。`weight = 0` 的定义或 offer 不参与抽取；不存在的引用会拒绝整轮数据加载。

数据包重载不会按当前库存重新创造商品列表。已保存的定义和 offer ID 仍是实例身份；定义删除对应项后，该项不会被运行时解析。

## 世界表面显示与交互

售货机仪表显示五个商品行、当前页、数量、总费用和每项可购买余量。仪表基座属于终端实体模型；文字、图标、状态灯与实体按钮由世界表面 UI 叠加。按钮和滑轨的渲染、命中面及高亮边框来自同一组件锚点。

- 上／下按钮切换商品；
- 滑轨把购买数量限制在 `1..10`；
- `BUY` 提交当前商品和数量；
- 客户端内容仅用于显示，最终商品、数量、费用和库存均由服务器重新读取。

## 购买事务

一次购买在服务器的统一贸易事务串行边界内执行：

1. 复核玩家、终端完整性、贸易点 UUID、注册状态和模块定义；
2. 在锁内重新读取繁荣等级、选中 offer、数量和输出库存；
3. 按实际匹配结果得到每种具体 CargoGood 的消耗 `t` 数；
4. 扣除玩家实体货币；
5. 扣除贸易点输出库存；
6. 把结果物品写入该售货机的公共待领取区；
7. 按每种 CargoGood 的实际消耗量更新贸易点吞吐、动态价格计数和活跃度，并且整笔付款只记一次；
8. 提交后刷新仪表。

付款、库存、待领取物和经济记账都注册反向补偿。提交前任一步骤异常时按逆序恢复，不允许出现“已扣款但无物品”“已出物但库存未扣”或重复记账。

活跃度使用 `实际消耗 t × CargoGood.base_value × output_trade_weight`。现有整数累计字段按实际总 `t` 四舍五入，日内活跃度保留小数精度。

## 待领取区生命周期

购买结果不会直接进入购买者物品栏，也不会立即掉落：

- 物品保存在售货机方块实体 NBT 中；
- 任何玩家都可右键出货副方块领取，不校验购买者身份；
- 只插入玩家物品栏实际能容纳的数量；
- 物品栏已满时不取出；部分可容纳时只取出对应数量，剩余物品继续留存；
- 普通领取永远不会把溢出物强行丢到地面；
- 待领取区为空时不渲染出货箱模型；
- 多方块终端被拆除时，剩余待领取物在控制器位置按正常物品实体掉落，且清理流程保证只执行一次。
