# 数据包维护流程

## 数据入口

下表路径均相对 `data/<namespace>/`；逐物品基础属性必须位于对应物品自身的命名空间，其余定义使用各自配置命名空间：

| 路径 | 用途 |
| --- | --- |
| `cargoverse_item_properties/<form>/<物品路径>.json` | 一物品一文件：形态、每组质量、准入、贴花及直接运输条件；无运输归属标签 |
| `cargoverse_fluid_properties/liquid/<流体路径>.json` | 一流体一文件，位于流体自身命名空间；每桶质量、贴花和原生 mB 扣量条件，缺失时默认 1Kpg/1000mB |
| `cargo_containers/<path>.json` | 货柜型号定义 |
| `manufacturers/<path>.json` | 制造商等级、货物偏好、签约价格修正与 `starter_container` 初始货柜型号 |
| `player_profiles/<path>.json` | 许可证等级门槛、调度点与雷达统计参数 |
| `trade_points/resource_tables/<type>/<station_kind>/<name>.json` | 出售、收购与库存资源表；正式站点的 `station_kind` 为 `ground_station` 或 `sky_station` |
| `trade_points/trade_points_definitions/<type>/<station_kind>/<name>.json` | 贸易点定义；与资源表使用同一 `station_kind` |
| `trade_points/trade_points_subfunctions/shop_definitions/<path>.json` | 物品商店定义 |
| `trade_points/trade_points_subfunctions/cargo_manufacturing_platform_definitions/<path>.json` | 货柜制造台定义 |
| `trade_points/trade_points_subfunctions/registration_point_definitions/<path>.json` | 注册点定义 |
| `trade_point_structure_bindings/<factory\|market\|resource>/<path>.json` | 世界结构与贸易点定义绑定 |
| `structure/<path>.nbt` | 货柜与建筑结构模板 |
| `physics_block_properties/<path>.json` | Sable 方块物理属性 |

`data/cargoverse/item_storage_adapters.json` 是模组内置的已审阅验空适配 ID 清单，随模组装载，不是可由 `/reload` 动态扩展的适配逻辑。逐物品声明 empty_storage 不能为未知容器自动创建适配器。

子功能定义的资源 ID 不包含子目录名称。例如：

```text
data/cargoverse/trade_points/trade_points_subfunctions/registration_point_definitions/oasis.json
-> cargoverse:oasis
```

资源表、贸易点定义和结构绑定中的 `type` 只使用 `resource`、`factory`、`market`，结构绑定类别必须与目标贸易点定义一致。

## 编写顺序

1. 确定实际物品及组件准入，维护对应物品的基础属性 JSON；不建共享运输条件集、成员标签、抽象商品或物品全局价格。
2. 定义制造商、货柜型号、基础货柜映射和结构模板。
3. 按 schema 3 定义站点精确物品或液体报价、出售库存、收购限额及每份交付经验。液体使用 type=liquid／fluid；液体按 1000mB 一份、物品按精确最大堆叠组配置；尾量按实际份数结算。40 张正式自然表仍为空，A/B 测试物品表已填充。
4. 定义商店、货柜制造台与注册点子功能。
5. 定义贸易点，填写制造商、价格、活跃度、繁荣度、资源表和模块引用。
6. 定义世界结构绑定，并在结构中布置贸易点信息柜、业务终端和所需定位点。
7. 执行 `/reload`，检查服务端日志后在测试世界验证完整业务链。

字段格式分别见[货物类型](../01货柜系统/01核心系统/05_货物类型.md)、[货柜定义](../01货柜系统/01核心系统/02_货柜定义系统.md)、[制造商定义](../01货柜系统/01核心系统/08_制造商定义.md)、[资源表](../02贸易点系统/03_资源表定义.md)、[贸易点定义](../02贸易点系统/04_贸易点定义.md)、[货柜制造台定义](../02贸易点系统/05_货柜制造台定义.md)和[注册点与基础货柜定义](../02贸易点系统/06_注册点与基础货柜定义.md)。

修改 JSON 前的逐定义内容设计与数值推演见[数据定义设计](../10数据包定义与模板/README.md)。

## 加载与发布

物品／流体属性、制造商、货柜、基础货柜、贸易点子功能、资源表、贸易点定义和结构绑定统一校验，发布同一完整代。逐物品属性不依赖成员标签；同物品跨形态重复、非法物品/流体/组件、未注册贴花、悬空引用、重复绑定或数值越界拒绝新快照，保留上一完整代。价格和经验仅在交易配置定义，不向运输属性添加这些字段。各定义只使用已记录的字段接口，不给未知字段臆造运行时语义。

同一资源 ID 按数据包优先级覆盖整项定义；数组不会自动拼接。删除或改名资源前必须检查全部引用。

玩家档案定义由独立监听器加载，并要求 `cargoverse:default` 存在。执行 `/reload` 后，服务端配置及标签完成发布，再同步展示所需的有界物品名称/图标目录；不把全部运输配置广播给客户端；货柜不再维护来源批次。

## 运行时数据边界

- 已制造货柜保存设备、兼容性和当前 Load 快照；
- 已注册贸易点保存资源表中的具体货物、库存策略和模块定义 ID，不因重载改写目录；
- 同一定义重新注册时会同步解锁等级、补充新增模块并移除定义中已删除的模块；
- 已抽中的定义在重载后不存在时，对应功能不可用，不会换成其他候选；
- 已保存物品或组件无法恢复时保留原始载荷并隔离，不能按空柜覆盖；已有载荷的冻结运输规则不因配置重载被替换；
- 手动放置的终端和定位点必须显式绑定，不使用默认贸易点或终端坐标回退。

## 构建检查

按[变更验证策略](06_变更验证策略.md)选择受影响检查，不默认每次全量测试。例如，仅调整液体属性时，在模组根目录执行：

```powershell
.\gradlew.bat test --tests '*FluidCargoTest' --tests '*CargoMeasureTest'
```

涉及原生储罐、结算或装卸路径时再增加对应 GameTest；发布或跨系统重构时才按需要扩大范围。世界表面位置、多人竞争、运动结构与视觉效果仍需在 Minecraft 客户端检查。
