# 数据包维护流程

> 已实现：以下当前加载入口。预留字段和待验收边界以各系统页面为准。实际 JSON 不写文档说明注释。

## 当前入口

下表路径均相对 `data/<namespace>/`：

| 路径 | 用途 |
| --- | --- |
| cargo_goods/<class>/<good>.json | 具体货物，严格两段 ID |
| cargo_containers/<path>.json | 空货柜型号 |
| player_profiles/<path>.json | 玩家档案；雷达图、许可证经验阈值和货柜调度点预算 |
| manufacturers/<path>.json | 厂商特性和声望预留 |
| currency_groups/<path>.json | 货币组；货物与容器只能引用有效组 |
| trade_points/production_line_pools/<type>/<category>/<pool>.json | 生产线池 |
| trade_points/trade_points_definitions/<type>/<category>/<name>.json | 贸易点定义 |
| trade_points/trade_points_subfunctions/shop_definitions/<path>.json | 普通物品商店定义；由贸易点 `modules.item_shop.definitions_pool` 引用 |
| trade_points/trade_points_subfunctions/cargo_manufacturing_platform_definitions/<path>.json | 货柜制造台定义；由贸易点 `modules.cargo_manufacturing_platform.definitions_pool` 引用 |
| trade_point_structure_bindings/<factory\|market\|resource>/<path>.json | 世界结构与贸易点定义的严格加权绑定 |
| structure/<path>.nbt | 实体货柜／建筑模板 |
| physics_block_properties/<path>.json | Sable 方块物理配置 |

生产线池、贸易点定义和结构绑定的根路径不同；三者内部的 type 分组仅为 resource／factory／market，不可混放。结构绑定目录类别还必须与其引用的贸易点定义 ID 类别一致。

所有贸易点额外功能定义统一收在 `trade_points/trade_points_subfunctions/` 下。每个功能加载器剥离自己的子目录来生成 ID，例如 `shop_definitions/resource/general/default_shop.json` 的商店定义 ID 是 `namespace:resource/general/default_shop`，不是 `namespace:shop_definitions/resource/general/default_shop`。

已废弃入口 cargo_definitions、cargo_value_constants、cargo_materials、旧平铺 trade_points/type 定义不再用于新数据；本页提到它们仅用于辨识旧配置，不能创建兼容副本。

## 编写顺序

1. 定义货币组和具体 CargoGood，确定科技等级、标签与每 t 数据。
2. 定义制造商与容器，引用有效货物；配置结构模板。
3. 定义生产线池：明确输出货物，按标签／科技范围选择输入。
4. 定义贸易点：库存槽、价格、活跃度、繁荣度、生产池引用和功能模块。
5. 需要普通商店或货柜制造台时，先在对应的 `trade_points_subfunctions` 子目录添加定义，再从贸易点的 `modules.item_shop` 或 `modules.cargo_manufacturing_platform` 定义池引用。
6. 配置结构生成与终端绑定，在测试世界生成并检查实例。

完整可加载示例直接来自[货物](../01货柜系统/01核心系统/05_货物类型.md)、[容器](../01货柜系统/01核心系统/02_货柜定义系统.md)、[生产线池](../02贸易点系统/04_生产线池定义.md)、[贸易点](../02贸易点系统/05_贸易点定义.md)和[货柜制造台定义](../02贸易点系统/06_货柜制造台定义.md)。示例中每个引用都需要对应资源，不能只复制一个孤立 JSON。

## 已实现：加载与重载

CargoDataReloadListener 负责货物／厂商／容器、普通商店定义、货柜制造台定义、编译后的生产线池与贸易点定义的同轮交叉校验，通过后整体发布，不先应用半套新数据。`item_shop` 和 `cargo_manufacturing_platform` 的候选定义都必须存在；其他尚未注册专用加载器的模块引用由未来对应加载器负责进一步校验。PlayerProfileDefinitionReloadListener 严格加载玩家档案，并要求 `cargoverse:default` 存在；结构不完整会拒绝该次重载。旧 `shipping_stats_config` 不再注册。

执行 /reload 后检查服务端错误日志及客户端目录同步。任何悬空货物、货币、厂商、池或固定内部产线引用都应先修复关联定义；不能期待未知 CargoClass 的 none 兜底替代缺失引用校验。

同 ID 按数据包优先级覆盖整项定义，不自动拼接 arrays。删除货物或池时必须检查所有关联引用。

## 待验收：重载影响

- 已有容器保存自己的兼容性快照；为新货物测试兼容性时制造新容器。
- 已有贸易点保存具体生产线与输入绑定，重载不重新抽取；容量配置可改变，超额库存不会直接删除。
- 已注册贸易点保存各模块抽中的定义。重载不重抽已有模块；同定义再次注册会同步解锁等级、补抽新增模块并移除已删模块。删除已抽中的定义会让终端暂时不可用，不会静默换成另一个候选。
- 货物定义缺失时，已有货柜／绑定数据保留，但相关交易或产线暂停。
- 补装时快照与当前定义混用仍需修正；不要把“重载安全”解释为所有既有资产绝不受影响。
- 世界实体贴花更新、物理质量回写及交易异常恢复见[待验收清单](../00_重构状态与验收清单.md)。

## 结构绑定与安全测试

结构绑定使用严格的 `schema_version`、`structure`、`trade_point_definitions[].weight` 与 `trade_point_definitions[].definition` 结构。所有字段都必须显式填写；旧 `structures_pool`／`trade_point_id` 格式、空候选池、悬空引用、跨类别引用、重复结构和未知字段都会拒绝整次数据包重载，不再使用默认定义兜底。

结构绑定与贸易点、生产池、商店定义、货柜制造台定义在同一原子数据快照中校验并发布。自然生成成功后会注入贸易点实例 UUID，子终端共享该实例，而不是每台终端复制库存。完整格式与错误清单见[贸易点结构制作指南](../02贸易点系统/02_贸易点结构生成层与制作规范.md#8-绑定贸易点定义)。

当前存档版本见[运行时与存档](../01货柜系统/01核心系统/07_运行时与存档.md)。无旧格式迁移。测试使用新世界或事先备份，不通过删除世界目录“修复”格式问题。

自动化构建命令为 `gradlew.bat build --no-daemon test --rerun`；实机验收另行记录，不能用编译成功代替游戏运行结果。
